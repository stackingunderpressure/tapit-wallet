# Carpenter opinions — Phase 5c-i-δ (the inbox in the People tab)

## Section 1: What I did.

This is the cut where the wallet stopped being a network-capable artifact and started being a network-active one — on opt-in. The previous three cuts had shipped the crypto, the wire client, and the Wallet-internal seam, but none of them actually made a connection to a relay. The user could not see anything. This session closed that loop. The wallet now has a settings toggle, a transport lifecycle in `WalletProvider`, and a small panel at the top of the People tab that lists incoming envelopes when they arrive.

The first move was adding a new field to the preferences schema. The Prefs interface now carries `nostrTransportEnabled: boolean`, and `DEFAULT_PREFS` sets it to false. Default-off, not default-on, because subscribing to a relay set is not a neutral act — it broadcasts to every relay in the default list that "this pubkey is online right now," which is exactly the kind of metadata the Mycelium privacy posture is careful about. The user has to opt in. The Settings screen grows a new section above the local-backup block, titled "Mycelium network," with a one-paragraph explainer of what enabling it lets the wallet do, plus a smaller privacy-note paragraph that names the trade-off plainly: subscribing tells the relay set your public key is online; keep this off until you want to be reachable.

The second move was the lifecycle wiring in `WalletProvider`. Right after the existing anchor-worker effect, a new `useEffect` reacts to two signals: the wallet phase being `unlocked` or `needs-identity`, and the `nostrTransportEnabled` pref being true. When both are true, it opens a connection through the `connectWallet` helper from the transport feature; when either goes false (operator locks, signs out, or toggles off), the cleanup runs and closes everything down. The on-envelope callback collects each incoming inbox envelope into a piece of provider state, deduplicating by event id so the same envelope arriving from multiple relays only lands once. The piece worth pointing at: `connectWallet` is loaded by dynamic import, not static import, so the transport stack — the WebSocket client, the NIP-44 encryption surface, the relay list, the inbox glue — only loads when the operator actually opts in. Users who never enable the network never download that code. The bundle-budget script names the resulting code-split chunk and caps it at five kilobytes gzipped; current is about one and a half. The `WalletProvider` chunk itself landed at 5.33 KB gz against a 5.5 KB budget — close to the wire, intentionally. Future additions to `WalletProvider` will almost certainly need their own dynamic imports.

The third move was the inbox surface. A new component, `InboxPanel`, lives in the transport feature alongside the rest of the wire layer. It renders a small accent-colored card at the top of the People tab whenever there are envelopes waiting. Each envelope row shows the attestation kind (Journal, Relationship, Credential, and so on, just title-cased from the kind string), the sender's pubkey shortened to first-eight-dot-dot-last-four for legibility, the receive time formatted with `toLocaleString`, and two buttons. Copy puts the verified-and-decrypted envelope JSON onto the clipboard so the operator can paste it into the right modal — `AbsorbCosignModal` for envelopes that need their signatures merged, `CosignAsWitnessModal` for envelopes that need a counter-signature, the membership-receive modal for credentials. That manual paste step is intentional: auto-routing to the right modal based on envelope kind is the next cut, not this one. Today the operator sees the envelope, knows it arrived, copies the bytes, and pastes them into the existing flow. The path works end to end; it just goes through one extra step that the next cut removes.

The fourth move was nutrition for the bundle-budget script. The dynamic import created a new content-hashed chunk named `connectWallet-<hash>.js`, and Rollup also hoisted out the tiny `parseEnvelope` helper into its own chunk now that three features share it. Both were getting matched by the unrecognized-chunk catch-all, which is fine but means a future growth event would only surface against the generic 3 KB cap. I added named budgets for each — five kilobytes gz for the transport opt-in chunk with headroom for the next phases, eight hundred bytes for the parseEnvelope hoist that should stay nearly nothing.

All eight gates green: tapit-attest typecheck, lint, ninety-seven of ninety-seven tests (four skipped network-deps, unchanged); wallet typecheck, lint, thirty-one of thirty-one tests, build with bundle budgets all clean. Pushed to the working branch as commit `2679e13`. Not pushed to main this turn. The branch is now four commits ahead of main with the full 5c-i slice — primitive, wire client, Wallet wire-up, and now UI.

## Section 2: What you could do better.

Three things, in increasing order of urgency.

The smallest is a question of UX polish I deliberately did not chase. The Copy-to-clipboard pattern is correct but the "paste into the right modal" instruction lives only in the inbox panel's subheader, in small text. A real user who turns the toggle on and gets an envelope is going to wonder which modal. The next cut, which adds auto-routing, makes this moot — but if for some reason the next cut slips, a brief inline hint of "Copy then paste into a Cosign-as-witness modal" might be worth it. Today it is fine because no one is using this yet.

The middle thing is that I added the transport effect's dependency array as `[phase, prefs.nostrTransportEnabled]`. The whole phase object is in there. That is following the existing anchor-worker pattern in the same file, but it has a subtle consequence: every time `phase` changes (which happens on landing-after-unlock when holdings load), the effect re-runs. That tears down the transport connection and opens a new one. In practice the lifecycle settles fast and the close-and-reopen finishes inside a single render cycle, but it would be cleaner to depend only on `phase.kind` and an extracted wallet reference. The anchor-worker pattern has the same shape and has not caused problems; I matched it for consistency. If the connection cost ever becomes meaningful — say, real network handshakes on every render — this is the place to look first.

The biggest thing is the NIP-44 reference-vector cross-check I have been flagging since 5c-i-α landed. This cut is the one after which the operator can flip the toggle and start exchanging encrypted messages with the wider Nostr world. Until those vectors run through `encryptTo` and `decryptFrom` and match byte for byte, "we speak NIP-44" is a faith claim. The internal round-trip and tamper tests prove our implementation is self-consistent, but they do not prove a third-party NIP-44 v2 client could read what we wrote. If you flip the toggle and field-test with two of your own wallets, you will not catch this gap because both ends are running our code. The right time to verify the vectors is before the first cross-implementation test, which is now genuinely imminent. Fifteen-minute job: copy the vectors from the NIP-44 spec repo, write a test that runs each one through the implementation, run it.

## Section 3: The bigger picture.

The shape of this cut is worth seeing as a small case study in how privacy-aware defaults travel through a codebase. The toggle is the obvious surface — a switch in settings. But what makes the toggle honest is the architecture underneath it. The pref defaults to false. The provider does nothing when the pref is false. The transport module is not even loaded into the browser when the pref is false. The bundle-budget enforces that fact mechanically — if a future refactor accidentally pulled `connectWallet` into a static import path, the budget check would fire and stop the build. So the privacy posture is not just a sentence in the UI; it is a property of the running code that the tool chain helps protect. That is the mechanism-over-prose pattern showing up again, this time on the network-opt-in surface.

The other shape worth pausing on is what just landed in three small cuts that would have been hard to land as one large cut. Last week the wallet had no network at all. This week it has a NIP-44 primitive, a substrate-agnostic transport interface, a Nostr WebSocket implementation, a Wallet that owns the keys it signs and encrypts with, and a UI that surfaces incoming traffic to the operator behind an opt-in toggle. None of these is large by itself, and each landed with its own tests, its own gate cycle, its own three-section opinion. The α/β/γ/δ slicing the operator blessed has paid off in a way that makes the next two slices — 5c-i-ε (auto-routing) and 5c-ii (remote handshakes Tier R) — feel like the same kind of small. That cadence is the thing I would protect.

The deeper point is what the wallet is now structurally capable of. Two people who shook hands in person yesterday can each open the Mycelium toggle today and the next time one of them sends the other a co-sign or a counter-signed handshake or a membership credential, it will land in the other's inbox without either of them having to be in the same room. The relay never sees the plaintext; the wallet verifies the envelope before showing it; the operator decides what to do with each one. Tomorrow when 5c-i-ε lands, the operator will not even have to copy and paste — the envelope will route itself into the matching modal. The day after that, with 5c-ii, two people who have never been in the same physical room will be able to do a remote handshake at Tier R, labeled honestly as the weaker tier. The network is no longer a sketch on a doctrine page. It is software that runs.

There is one quiet note worth ending on. The reason any of this works is that the wallet refuses to do anything across the network without the operator turning it on. That is the only way a sovereign system can grow a network without becoming the thing it was trying to replace. The toggle is the line between "this is your tool" and "this is the platform you joined." The wallet keeps the line on the user's side. That is the prime directive holding underneath everything else this codebase does, and every cut after this one will inherit it.
