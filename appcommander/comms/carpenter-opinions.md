Phase 3 is the Layer 2 inter-app deeplink pathway. Commit `e789d2c`. A third-party app or another wallet can now construct a URL pointing at `/sign` with a base64url-encoded SignRequest in the query parameter — origin name, intent, attestation kind and tier, subject, claim fields, callback URL, optional nonce. The wallet decodes it, validates every field strictly with typed error codes (`invalid_request`, `unsupported_intent`, `unknown_kind`, `unknown_tier`), and renders a plain-English approval screen. The screen is the product per `DESIGN.md` §9 — it shows the requesting app's claimed origin AND the actual host of the callback URL the operator will be redirected to, so a non-technical user can sanity-check that the destination matches what the request claims to be from rather than just trusting a display name. Per attestation kind, the render surfaces the most user-relevant fields (display_name and pubkey for identity, name and issuer for credential, text and category for journal, etc.) with any extras shown as a secondary list. On Approve, the wallet calls `wallet.attest` with the request's fields (which internally wraps tapit-attest's `createDraft` + `signEnvelope`), holds the result, persists the wallet, queues the new envelope for OpenTimestamps anchoring exactly the same way a self-authored entry is, and redirects to the callback URL with a SignGrant in a `grant` query parameter. On Decline, it redirects with a structured SignDecline carrying the reason code and an optional human-readable detail. Malformed requests show an error screen with the parse error's code and a "return error to caller" button only when the parser was able to extract a callback URL. Nostr NIP-46 stays explicitly out of v1; the same SignRequest/SignGrant message shapes will carry over to a NIP-46 transport later without changing the wallet's approval flow.

Phase 4 is selective leaf disclosure — the "math, not trust" thesis principle's most user-legible demonstration. It landed in two commits because it required real library work plus the wallet-side UI. The library half at `c0bcda1` exports `metaHash` from `envelope.ts` so the verifier can recompute the canonical attestation digest from the envelope's meta-fields plus a recovered claim root using the same hash function the signer used, and replaces the stub `disclosureProof` in `field-tree.ts` with a real implementation. A `DisclosureProofBundle` carries the envelope meta (v/kind/tier/subject/issuedAt), the disclosed leaf node by name and value, a list of sibling-hash steps walked from root down to the leaf, and the envelope's signatures copied verbatim. `verifyDisclosureProof` reverses the walk — starts with the leaf's hash, reconstructs each branch hash by placing the running hash at the recorded path index and the recorded siblings at their original positions, ends at the recomputed claim root, computes the attestation digest via `taggedHash('tapit/root', metaHash || claimRoot)`, and runs quorum-of-good signature verification on the carried signatures. Five new tests cover the round-trip on a signed attestation, the non-disclosure property (other leaves never appear in the serialized proof — they're hashes), tamper detection on both the disclosed leaf and the meta-fields, and the error paths for malformed leaf paths. The library now stands at eighty-two tests total, seventy-eight passing, four skipped (the same corrupted-OTS-fixture baseline).

The wallet half at `6ee7f34` is the user-facing flow. A new disclosure feature folder with a `leafIndex` helper that walks the claim tree and returns every disclosable leaf with its slash-delimited path, a `parseDisclosureProof` shape-validator so a malformed paste surfaces as a friendly error rather than crashing in the library, a `ShareProofModal` accessible from any entry's detail page that lists every leaf in the claim as a radio-pick and generates a copyable JSON proof when the operator selects one, and a `VerifyProofScreen` at the `/verify` route. The `/verify` route deliberately lives OUTSIDE the `AuthGate` because the verifier is a third-party context — anyone with a copy of the wallet PWA who needs to check a proof someone gave them, possibly without a wallet of their own. They paste the proof, the wallet runs `verifyDisclosureProof` against the math, and the result page renders the disclosed field's name and value, the envelope meta the signatures were bound to (kind, tier, subject, issued_at), each signer's verification status with a check or X mark, and any errors from the quorum-of-good check. Valid proofs render emerald; invalid render amber. Never a JSON dump.

## What you could do better

The biggest honest flag is that the v1 surface is now feature-complete for what you described, and feature-completeness without browser verification is exactly the failure mode the doctrine warns about. Every line of this work has been proven only at the gate level — typecheck, lint, vitest, build — not at the feature level. The deeplink approval flow has not been walked against a real third-party app constructing a real request. The disclosure proof round-trip has not been walked between two real browser tabs. The `/verify` route has not been accessed by an unauthenticated visitor. The fetch-timeout in the anchor worker has not been exercised against a deliberately-slow calendar. The idle-timeout has not been verified to actually fire after thirty minutes of real inactivity. Every one of these has unit-level confidence; none has integration-level confidence. The right operator move when you're back from the Netlify wire-up is the browser-verify walk in PLAN.md's closing section, in order, and any stall is the next session's first business.

The second flag is the bundle bloat trend I named two sessions ago is still monotonic. JournalDetail crossed from four-point-two to four-point-eight-seven kilobytes gzipped this block to carry the share-proof modal; the attest chunk grew from twenty-five-point-eight to twenty-six-point-four. Login surface stays unchanged at about a hundred-ten kilobytes because everything new sits behind `AuthGate` and `React.lazy`, but the post-auth surface is creeping up. Worth a bundle-audit pass before the next meaningful feature lands — split anything crossing ten kilobytes gzipped, hoist hot common code into shared modules, and re-check that the login surface still ships without any wallet-core weight.

The third flag is the same one I keep raising: the pre-push adversarial diff review caught a bug this block too (the SignApprovalScreen copy bug). The pattern is doing its job. It would do more of its job mechanically. A pre-commit hook that greps new code for function names overlapping `tapit-attest`'s public exports would catch the next variant of the digest/envelopeId bug class without me having to remember to look. I keep logging it as a follow-up and not implementing it. Worth doing before the operator's parallel infra work finishes.

## The bigger picture

The wallet has crossed a threshold this turn that's worth naming. Phases One through Four are the original DESIGN.md v1 scope plus the operator's diary-first reframe; that scope is now all running. A person can open the PWA on their phone, sign in with email, set a passphrase, give themselves a name, write a signed and OpenTimestamps-anchored journal entry about their grandchild's birth with a photo attached, send the envelope to their wife via iMessage and absorb her witness signature into the wallet's copy, hand off custody of the grandchild's identity thread to their daughter when the time comes, save any entry to their own files for sovereign backup, toggle cloud-sync off if they want full sovereignty, lose nothing across a wallet restore on a new device because anchors get attached back onto held attestations, re-prompt for the passphrase after thirty minutes of inactivity, approve an inter-app sign request from a third party via a deeplink that shows them what's being signed in plain English, and selectively disclose a single field of any signed attestation by handing a verifier a self-contained proof bundle they paste into `/verify` and see check out. That is the wallet you described in the brief, running in code. The math is the truth on every surface; no platform sits in the loop on any of it.

The deeper observation is that all four wallet layers from CLAUDE_ROOT.md are now represented in shipped code. Layer One is the keypair from `tapit-attest`. Layer Two is the inter-app pathway via the deeplink shipped in Phase 3. Layer Three (the Mycelium peer network) is deferred to its own spec per the doctrine; the diary-first brief named what should fill it. Layer Four (the wallet bot) is explicitly out of v1 and lives as dormant scaffolding under `src/features/{persona,snapshot-builder,suggested-questions,temporal}` with paused manifests. The architecture's promise is now legible in the code rather than just in the doctrine. That's the difference between the wallet that existed at the start of this conversation and the wallet that exists now.
