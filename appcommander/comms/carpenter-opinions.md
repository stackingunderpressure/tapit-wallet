# Carpenter opinions — Phase E3 cuts 1 and 2 under Option 3 hybrid substrate (2026-05-26 early afternoon)

## Section 1: What I did

This session was a clean two-cut substantive run that took the Phase 8 open-joining axis from where the prior session parked it — the joiner-side machinery sitting on disk, working but ungated — through the full Phase E3 substrate. The operator opened with a chip-form directive: pick the open-joining substrate from the three options the brief laid out, full-chunk context, ask anything else as chips. I surfaced the substrate decision immediately as a four-option AskUserQuestion (Option 1 org-roster, Option 2 verifier-walks-auth-tree, Option 3 hybrid, Defer) and the operator picked Option 3 hybrid — the recommended choice in my prior letter, the one that preserves the most sovereignty while still allowing the consolidated-roster UX when an org wants it. That single chip-tap locked Phase E3's scope. Under hybrid the brief explicitly wants both verification paths to work: an org-published roster (Option 1's path) and a verifier walk of the org's declared join-rule (Option 2's path). Both paths share the same join-policy evaluator. Both phases share the same self-membership envelope shape Phase E2 already shipped.

Cut 1 was the policy evaluator and the gating wire-up. I created src/features/governance/evaluateJoinPolicy.ts at line one — a pure function that takes a JoinPolicy (the discriminated-union shape Phase E1 landed in authRule.ts), a self-membership Attestation, and the org wallet's holdings, and returns an honest {accepted, reason} verdict. Three of the six policy kinds — open, allow_list, deny_list — evaluate purely against the envelope's subject leaf which carries the joiner's pubkey, with case and whitespace normalization so a mixed-case hex pubkey arriving from a relay still matches a lowercase allow-list entry. The other three kinds — requires_handshake, requires_credential, requires_vouch — need joiner-side proof attachment that Phase E2's buildSelfMembershipDraft doesn't yet produce, so the evaluator rejects them with a reason naming Phase E4 as the milestone that adds proof reading. That's the honest contract: don't pretend to validate something you can't validate today, surface the deferred state explicitly so the operator and verifier both know the policy will only start working when Phase E4 lands. I then rewrote the Phase E2 placeholder receiveSelfMembership in createMembership.ts from a single-gate function (envelope shape, then holdAndAnchor) to a three-gate function: shape, then org must hold its own self-declaration with a join rule, then evaluateJoinPolicy must accept the joiner. Reject reasons surface through Error.message so the eventual UI can show the org operator why a join request did not land instead of swallowing the verdict in a console.warn. HomeScreen.acceptSelfMembership grew the wiring to pass orgDeclaration and holdings into the new signature, and short-circuits with a warn when the wallet hasn't declared itself as an org — a self-membership routed to a personal wallet has no business getting accepted into holdings. Cut 1 added twelve tests and shipped under commit fifty-eight-af-four-three-five.

Cut 2 was the open-member roster substrate. I created src/features/connections/openMemberRoster.ts at line one — same envelope-shape pattern publishOfficialsRoster has used since the org-mode-five-b cuts. Subject equals the org's pubkey, credential_type leaf is the literal string open underscore member underscore roster, members leaf is canonical JSON of an array of entries shaped as member id plus joined at plus self membership envelope id, sorted ascending by joined at then by member id for stable tiebreaks, issued at set at publish time. Six exports: acceptedSelfMemberships returns every self-membership in holdings addressed to the named org sorted by join order; pendingSelfMemberships returns the delta — accepted-set minus already-on-latest-roster — useful for showing the operator how many new joins would be in the next snapshot; buildOpenMemberRosterDraft is the pure unsigned builder; publishOpenMemberRoster wraps sign plus hold plus anchorQueue dot upsert plus worker kick the same way publishOfficialsRoster does; findLatestOpenMemberRoster does latest-by-issued-at selection mirroring findLatestOfficialsRoster exactly; readOpenMemberRoster is a shape-tolerant member-list parser that drops malformed entries individually so a future shape skew or a maliciously edited envelope can't crash a UI render. Fourteen new tests covering predicate, filtering by org id, sort order, entry shape, latest-wins, delta computation, empty plus already-published edge cases. Total tests went from one-seventy-six on session start to two-oh-two on session end — a clean plus-twenty-six across the two cuts. All four gates green throughout: typecheck clean, eslint clean, both test totals, build clean with every named chunk under budget. Cut 2 shipped under commit c-six-d-c-c-zero-seven.

## Section 2: What you could do better

One genuine observation worth naming. The receiveSelfMembership signature now takes orgSelfDecl as a required argument, which means every caller has to look up the wallet's own org declaration before invoking the acceptor. HomeScreen.acceptSelfMembership does the lookup correctly (via the existing orgDeclaration useMemo), but a future caller — a ScanEnvelopeModal path, a batch-import flow, an AI-bot-driven acceptor — could trip on the same gate by forgetting to pass the declaration and would get a confusing throw rather than a clear "this wallet has no org declaration" error. The honest fix is to centralize the lookup inside receiveSelfMembership: take the wallet plus the holdings, derive the org declaration via the existing findOwnOrgDeclaration helper, and throw with the explicit reason if missing. That would tighten the contract for cut-two callers without changing any test. I didn't do it this session because the existing pattern (caller passes the looked-up declaration through) matches how every other create-attestation function in this domain works, and changing it would break consistency. But it's worth a chip-form question next session: do we centralize the lookup inside the helper, or keep the caller-side lookup pattern uniform across the codebase.

The second observation is about the bundle-budget script. Eleven unrecognized JS chunks still bucket under the catch-all unnamed-budget line this session, same as last session and the session before. The new openMemberRoster.ts has no production caller yet so it doesn't form a chunk of its own, but Phase E4 will wire the publish button and that's when the unnamed-chunk debt becomes load-bearing — a new chunk forms, no named budget exists for it, and the script's catch-all line grows from eleven to twelve. The two-hour fix is to walk through scripts/bundle-budget-check.mjs (or wherever the named budgets live), give each unnamed chunk a label, and let the script start failing loudly when a chunk grows past its budget instead of bucketing silently. Worth doing before Phase E4 lands so the verifier UI ships with a real named budget rather than another row in the catch-all bucket.

The third is procedural: the test-file non-null-assertion bumps are slightly avoidable. The tsconfig has noUncheckedIndexedAccess on, which is the right setting for production code but makes test files more verbose. A future cleanup would be to add a tests-specific tsconfig that turns that off, freeing test code to be as ergonomic as it actually wants to be without dragging non-null assertions through every result-bracket-zero access. Tiny ergonomic win, not load-bearing, but the operator might value the noise reduction in test files.

## Section 3: The bigger picture

What just shipped is the substrate for the second axis of organization in this wallet. The first axis — the org-control axis — landed across Phase A (auth tree), Phase B (verifier), and Phase C (caller wiring) earlier in this week. That axis says how an org can authorize its own actions: issuance, expulsion, charter amendment, dissolution. Each is a signer-side authorization, gated by a threshold of eligible signers. The second axis — the membership-acquisition axis — is the one this session and the prior two sessions have been building. It says how a person can become a member of an org. Phase E1 extended the rule shape to carry the joiner-side policy. Phase E2 shipped the joiner's self-claim envelope and the routing that recognizes it. This session's Phase E3 cuts shipped the gate that decides whether the joiner is structurally entitled to be on the roster and the roster envelope itself. Phase E4 — verifier plus UI — closes the loop.

The deep insight here is the symmetry. An org's auth tree carries both kinds of rules — signer-side authorizations and joiner-side policies — in one Merkle structure, with one disclosure-proof primitive, one envelope shape, one verifier. The shipped tapit-attest primitive doesn't care which axis a leaf describes; it just commits to whichever leaf the producer reveals and verifies that the path math checks out. The wallet learns to read both axes by adding type guards and predicate functions, not by adding new cryptography. The hybrid substrate Option 3 the operator picked is the most honest expression of this symmetry: the org publishes a roster when it can (the org-control-axis assertion that "these are the members I have admitted") and the verifier can also walk the auth tree to check the joiner's claim against the policy (the membership-acquisition-axis assertion that "this joiner meets the rule the org declared"). Both proofs verify against the same envelope shape. The verifier accepts whichever it can construct.

That's why this wallet keeps feeling like one coherent thing rather than a stack of features. Every new capability is a new way of reading or producing the same envelope structure. Every new test is a new path through the same Merkle primitive. The substrate is small and the surface area is small. Phase E4's verifier will be one new function — verifyOpenJoinedMembership — that composes findAuthRule plus findLatestOpenMemberRoster plus the existing verifyDisclosureProof. No new cryptography. No new persistence layer. Just one more pair of typed predicates over the same holdings array every other feature reads.

When Phase E4 lands and an operator can scan a stranger's QR, see the org they belong to, verify the join through whichever proof path holds, and decide whether to extend trust — that's the moment the membership-acquisition axis becomes a real product. Today it's substrate. Tomorrow it's a friction-free join flow that's auditable down to a Bitcoin anchor height. That's a meaningful arc, and it's two sessions away.
