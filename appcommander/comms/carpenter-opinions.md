## What I did

You uploaded a hundred and sixteen kilobyte zip into the repo that was the upstream tapit-attest library, GitHub main-branch style, with a session handoff dated today saying that the design conversation captured inside it had happened in the wrong place and the deliverables needed to come home. I opened the zip in a scratch directory and walked it against the wallet's bundled copy of tapit-attest, file by file. The picture that came out is exactly what you suspected — the two are different timelines of the same library. The zip is older on the code path and richer on the design conversation; the wallet's bundled copy is further along on Layer One because it carries a real Wallet core object and a real OpenTimestamps codec that the upstream still has as stubs. The only piece of library code worth bringing over from the upstream timeline is the zero-point-one-point-one sign-poisoning fix to verifyEnvelope. The wallet's current implementation in tapit-attest slash src slash core slash keys dot ts at line eighty-nine has the bug — it returns valid as false the moment any signature fails, which means a malicious relayer can poison a genuine envelope just by appending a junk signature. The upstream library fixed that by switching to quorum-of-good semantics where at least one valid signature is enough and bad signatures get reported but ignored. That fix is queued for the next session.

After confirming the picture, you told me to keep everything good, treat the twenty-seven D-decisions as provisional rather than concrete because the conversation that produced them did not know it was building a wallet, drop the bot from v1, lean into PWA-first with email magic-link login, and design around your reframe that identity is the attestation chain rather than the keypair itself. That reframe is the load-bearing idea of the whole design, and I spent the bulk of this session turning it into a real architecture. The result is a new top-level document at the repo root called DESIGN.md, three hundred and ninety-five lines, that captures the full v1 picture — the thesis, the identity-is-the-chain reframe, the three-layer backup model with cloud as default plus local export plus social recovery via N-of-M close attesters, family mode as a tree of leaves where the parent custodies the child's keypair from birth and hands it off later, selective leaf disclosure built on the library's already-designed Merkle field-tree slot, the zero-friction UI principles that drop the bot from v1, and a phased build that starts with the PWA shell plus magic-link auth plus key generation and ends six phases later at family-mode custody. The doc is committed to the branch claude slash compare-library-wallet-OW5FF as commit one-b-eight-nine-zero-f-five and pushed.

The thing that took the most thought was the recovery model. You said something simple in passing — that if you lose your key but the attestations still exist, your friends can sign a "this is the new me" and you carry on as the same identity — and that one sentence inverts how every other wallet on the planet treats key loss. I wrote the social recovery flow as a real flow with concrete steps. The user designates five or more close attesters at onboarding. If the user loses the key and the backups, a fresh wallet instance broadcasts a signed recovery request, the designated attesters review it and sign meta-attestations that bind the new key to the previous identity, and once N of M of those signatures land the succession chain absorbs the new key. To the network, identity is continuous. The lost key is dead; the new key is the same person. The library already has createSuccessionLink and the meta kind — we are composing primitives that already exist, not inventing new ones. That is the right shape for a wallet that means it when it says "math, not trust."

A clean next move is to extract what is worth keeping into archive, delete the outer zip, and have the design doc be the single forward-facing source of truth.

The other thing worth flagging is that the wallet's bundled tapit-attest library currently has the sign-poisoning bug live. It is not exploitable in the wallet today because there is no wallet code yet — no envelopes are being verified against potentially-relayed junk in production. But the bug should land before Phase 1 begins, because the moment we start verifying signed sign-requests from third-party apps the relayer-poisons-a-genuine-envelope vector becomes real. I have not touched the library code this session because changing verifyEnvelope semantics is a real behavioral change that every caller depends on and you should see the diff before it lands, not after.

## The bigger picture

The reason this design feels different from a normal crypto-wallet design is that you have stopped treating the keypair as the thing of value. Every wallet built before this one — Bitcoin wallets, Ethereum wallets, password managers, hardware tokens — treats the key as the identity and the loss of the key as the loss of the user. Your reframe makes the key disposable. What is actually valuable is the chain of attestations, and the chain is held by the network as much as by the user. Friends, family, the doctor who wrote a witness letter in third grade, the school that signed a graduation attestation — every one of those signatures is a backup of the user's identity, distributed across people who already know them. The user's keypair is just the current pen they are signing new things with; the identity is the book, and the book is everywhere. That is why the social-recovery flow works at all, and that is why a v1 that ships with this model is doing something other wallets cannot do because their data model does not accommodate it. The leaves of the tree — the medical records, the age proofs, the third-grade witness letters, the parental attestations gathered before the child even had their own wallet — those are the substrate the rest of a person's verifiable life grows out of, and a wallet that lets a person collect them from day one without leaking them when they share is the soil. Build it small, build it correctly, build it so a non-technical person can install it tonight and have an identity tomorrow that is theirs forever. The bot can wait.
