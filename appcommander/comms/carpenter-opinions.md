# Carpenter opinions — Phase 5c-i-β (the Nostr wire client)

## Section 1: What I did.

This is the cut where the wallet learns to talk through a wire. Last session shipped the NIP-44 encryption primitive in tapit-attest — the format for an encrypted message to one peer. This session shipped the substrate underneath: the actual websocket conversation with a Nostr relay, the event-construction grammar, and the high-level "send this envelope to that pubkey" layer that the rest of the wallet will eventually call. Five small modules in a new feature folder at `src/features/transport`, plus a one-function addition to tapit-attest, plus ten tests, plus the feature registry entry.

The very first thing I did was add `signDigest` to tapit-attest. It takes a thirty-two-byte digest and a private key and returns a BIP340 Schnorr signature as hex. The wallet uses it for Nostr event ids, where you canonically serialize the event fields, sha256 them, and sign the hash. tapit-attest already had `signEnvelope` which does the same thing but for an attestation digest specifically; what was missing was the lower-level primitive that takes any digest. Two extra lines really — a length check on the digest and a length check on the key, then call into `@noble/curves` schnorr.sign. The whole reason this lives in tapit-attest rather than the wallet is the never-re-implement-tapit-attest rule. Schnorr signing is library territory; the wallet imports it.

Then the wallet got the transport feature. `transport.ts` is a single TypeScript interface — `Transport` with three methods, `publish` and `subscribe` and `close`, plus a `Subscription` returned by subscribe so the caller can stop listening. This is the seam that makes the substrate swappable per D-06: today the only implementation is Nostr-over-WebSocket, tomorrow it could be libp2p, gossipsub, or anything else that can route an event from one pubkey to another. `nostrEvent.ts` is the NIP-01 grammar — `buildEvent` takes a pubkey, a private key, a kind, content, and tags, canonically serializes them into the magic `[0, pubkey, created_at, kind, tags, content]` JSON array, sha256s it, signs the hash with our new `signDigest`, and returns a fully-formed Nostr event. `verifyEvent` does the reverse — recomputes the id from the canonical form, checks it matches, then verifies the signature with tapit-attest's existing `verifySignature`. A relay can hand us anything; we drop it on the floor if it does not check out. The custom event kind for Tapit envelopes is `9573`, in the regular-events range so relays persist it for async delivery, picked because no major NIP claims that number.

`nostrTransport.ts` is the actual WebSocket client. One websocket per relay, all running in parallel. When `publish` is called we encode the NIP-01 `["EVENT", event]` frame and send it to every relay. When `subscribe` is called we encode `["REQ", subId, filter]` and send that to every relay, keeping the subscription record so we can re-issue it on reconnect. Reconnect is exponential backoff, starting at one second and capped at thirty. There is a small outbox per relay that catches publishes issued while a socket is down, and flushes them when the socket comes back. Incoming events are deduplicated by event id across relays — the same event arriving from five different mirrors fires the subscription handler once. The WebSocket implementation is injectable so tests can pass in a fake.

`encryptedInbox.ts` is the layer the rest of the wallet should actually call. `sendEnvelopeTo` takes a tapit-attest envelope, the recipient's pubkey, the sender's keypair, and the transport, then JSON-stringifies the envelope, encrypts it with `encryptTo` (the NIP-44 primitive from last session), wraps the ciphertext in a Nostr event of kind 9573 with the recipient in a `p` tag, and publishes. `subscribeInbox` runs the reverse: subscribe to kind 9573 events with the wallet's pubkey in their `p` tag, on each one verify the Nostr signature, decrypt the ciphertext with the wallet's private key (which will fail the MAC if the message was not actually addressed to us, or if the relay tampered with the bytes), then re-parse through the existing `cosigning/parseEnvelope` helper into a typed `Attestation`. Anything malformed at any layer drops silently — exactly what you want from a hostile relay. The tests verify all of this with an in-memory fake transport and an injected fake WebSocket; no real network was touched.

`defaultRelays.ts` is just a list of five widely-used public relays — `wss://relay.damus.io`, `wss://nos.lol`, `wss://relay.snort.social`, `wss://relay.primal.net`, `wss://nostr.wine`. The wallet ships with these so it works out of the box; a sovereign user will swap in their own when settings exposes the list as editable in a future cut. All eight gates green in both packages: tapit-attest typecheck, lint, ninety-one of ninety-one tests; wallet typecheck, lint, twenty-nine of twenty-nine tests, build with bundle budgets all clean. Pushed to the working branch as commit `5f65f3c`, not pushed to main this turn.

## Section 2: What you could do better.

Two honest observations and one piece of homework.

The piece of homework is the same one as last session, restated for completeness: the NIP-44 primitive at the heart of all of this still has not been cross-checked against the upstream reference test vectors. If a real third-party Nostr client implementing NIP-44 v2 picks up one of our messages, it should round-trip. The internal tests prove our implementation is self-consistent and rejects every form of tampering I could think of, but they do not prove byte-for-byte interop. Until we run the reference vectors, "we speak NIP-44" is a faith claim and not a proof claim. Doing this before 5c-i-γ ships is a good idea, because 5c-i-γ is the cut where real messages start going to real relays and being read by real wallets.

The first observation is about a flaky test I noticed in tapit-attest while running the gates — not caused by anything I changed. The test at `tapit-attest/test/encryption.test.mjs:22` claims that flipping the first byte of an AES-GCM ciphertext fails the auth check. The "flip" is literally replacing the first two hex characters with `"00"`. If the original first byte happens to be zero — which is a one-in-two-hundred-fifty-six chance — the "tampering" is a no-op and the test fails because decryption succeeds. I saw it fail once, then pass on retry. The fix is one line: XOR the byte instead of replacing it, or replace with a guaranteed-different value. Tiny, but worth picking up next time someone is in that file.

The second observation is about the event kind I picked, `9573`. I chose it because it is in the regular-events range — relays persist it, so async delivery actually works — and because no major NIP claims that exact number. But "no major NIP claims it" is weaker than "the Nostr community has reserved it for this use." The right move once we ship is to propose a NIP, or at minimum to socialize the choice with the Nostr-tooling community, so we are not in a future collision dance. For today it is a swappable constant and the cost of changing it later is one symbol rename, so not urgent — just worth flagging.

## Section 3: The bigger picture.

Two cuts ago the wallet only knew how to hold attestations on one device. Last cut it knew how to encrypt a message to one peer. This cut it knows how to send that encrypted message across the open internet, through a relay that cannot read it, to a peer who can. That is the shape of a network being born. The very next cut wires this into the actual user-facing flows — once `5c-i-γ` lands, an existing in-person handshake can complete asynchronously, and a person who walked away from a half-finished co-sign can resume it from across the world.

The architectural shape worth pausing on is the layering. The wallet's UI knows nothing about Nostr. It knows about `sendEnvelopeTo` and `subscribeInbox`. The `encryptedInbox` layer knows about NIP-44 but not about WebSockets — it talks to a `Transport`. The `nostrTransport` knows about NIP-01 framing and WebSocket lifecycle but not about envelopes or encryption — it ships opaque byte payloads through `Transport.publish` and routes opaque events through `Transport.subscribe`. Each layer sees one floor up and one floor down. The day someone wants to put this on libp2p, the day someone wants to swap NIP-44 for a different peer-encryption scheme, the day someone wants to address peers by something other than pubkeys — each is a single-file change. That decoupling is not bookkeeping; it is the property that lets a sovereign system survive substrate decisions outliving their wisdom.

The deeper point is the discipline of the silent drop. Every layer in this stack assumes the layer below is potentially hostile. The transport receives a frame from a websocket and validates it is a parseable JSON array before doing anything with it. The encrypted inbox receives a Nostr event and verifies the id matches the content and the signature checks before trying to decrypt. The decryption layer requires the MAC to verify before yielding plaintext. The envelope parser requires the parsed JSON to assert-well-formed before becoming a typed `Attestation`. At every checkpoint, garbage drops to the floor without an error message, without a log line, without anything an attacker could turn into an oracle. This is not paranoia; this is what sovereignty looks like when the substrate is open. The relays are dumb pipes by design — they have to be, because we cannot trust them with anything — and the wallet works hard so they can stay that way. Tomorrow when the operator picks up two phones and walks through 5c-i-γ for the first time, that quiet posture will be what makes the network feel safe enough to actually use.
