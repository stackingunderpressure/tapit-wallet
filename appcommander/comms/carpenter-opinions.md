## What I did

You said "Yes" and I took that as "cut Phase 2 next," because that's what I'd named at the close of the last reply. Eighteen files moved in commit `c87e8a2` — six created, twelve modified — and the wallet went from a key-holding shell to a wallet that holds its first signed claim about itself. The change of state is real: a brand-new user now finishes onboarding holding an attestation, not just a keypair. That distinction is the whole point of the wallet, and Phase 2 is where it becomes visible in the UI.

The first-run flow gained a second screen. After the passphrase prompt creates the keypair and writes the encrypted snapshot, the user is asked for a display name on a separate screen — one field, autofocus, sixty-four character max. When they submit, the wallet calls `identityAttestation` from `tapit-attest` with three leaves on the Merkle field tree: `display_name`, `pubkey`, and `created_at`. The draft is signed by the wallet's own key, held on the wallet, and the snapshot is re-encrypted and re-persisted to both IndexedDB and Supabase. The whole transaction takes one passphrase entry; the passphrase is held in a `useRef` inside `WalletProvider` across the session so the post-onboarding save doesn't re-prompt. When the session ends — sign-out, expired auth — a `useEffect` on the session clears the ref so the passphrase never outlives the session.

On the home screen, three things are now true. The `IdentityCard` still shows the truncated pubkey with a copy button — that's the cryptographic identity. Above it now sits an attestation card that renders the held identity attestation as plain English: the display name large, the issue date as a friendly local-format string, the tier `routine`, and the words "self-signed" so the user can read at a glance that this is a claim they made about themselves. The "Plain English everywhere" UI principle from `DESIGN.md §9` is implemented here in real code; the card never shows a hex blob, a JSON dump, or a curve name. A backup-status banner sits above the cards when there's something to say: "Cloud backup is off" if cloud-sync was toggled off, "Cloud backup pending" if the first remote sync hasn't completed, "Cloud backup is more than a day old" if it's been over twenty-four hours. When everything is fresh, no banner. Sign-out moved off the home screen and into Settings where it belongs alongside the other policy controls.

The Settings feature is brand-new, with its own folder under `src/features/settings/`, its own `manifest.ts` declaring dependencies on `auth`, `wallet-core`, and `storage`, and its own lazy-loaded route at `/settings`. Three cards on the surface: a cloud-backup card with a real toggle (default on, persists to `prefsStore`, immediately re-saves when flipped back on so a freshly-enabled cloud sync pushes a current copy), a local-backup card with a passphrase-confirmed encrypted-blob download (filename includes the date so multiple exports don't collide, uses `Wallet.exportEncrypted` so the file is exactly the same `EncryptedBlob` shape stored remotely), and a session card with the sign-out button.

The storage layer needed a small extension to support the new policy knobs. `prefsStore.ts` is a fresh module: unencrypted user-level prefs keyed by `prefs:<ownerId>` in IndexedDB. The shape is two fields right now — `cloudSync: boolean` and `lastRemoteSync: string | null`. `walletStore.save` now reads the cloud-sync pref before deciding whether to write remote, records `lastRemoteSync` on success, and returns a `SaveOutcome` describing what happened where (local always, remote sometimes). Failed remote writes don't crash the save — the local copy stands and the next save reconciles. The `WalletContext` got bigger to thread holdings, the identity attestation, prefs, and the save thunk through to consumers. `useWallet` consumers can now write `const { wallet, identity, prefs, save, updatePrefs } = useWallet()` and have everything they need.

`PLAN.md` got rewritten in the same commit to match `DESIGN.md`'s six-phase structure, which is what `DESIGN.md` itself called for. Phases One and Two are marked DONE; Phase Seven plus is named explicitly as the bot scaffolding's launch slot and the entire post-v1 surface; the Mycelium peer network is named as deferred to its own spec. The old PLAN.md had five phases that didn't match the design doc and the operator had been reading two slightly different stories of what was being built; both files now tell the same story.

All four root gates ran clean — typecheck silent, lint zero-zero, vitest sixteen of sixteen tests passing (the manifest-registry test correctly picked up the new `settings` slug, no manual update needed), production build at two-point-seven-seven seconds across one hundred forty modules. The `tapit-attest` suite stayed unchanged at seventy-four pass and four skipped. Login-bundle posture is unchanged from Phase One — about one hundred ten kilobytes gzipped, because the new settings code and the expanded wallet provider sit behind `AuthGate` and `React.lazy`. The lazy chunks grew modestly: WalletProvider went from about six kilobytes to about ten (gzipped from two to three), HomeScreen went from one-point-six to three-point-four (gzipped from one to one-point-four), and the brand-new SettingsScreen chunk weighs in at about four kilobytes (gzipped to one-point-six). Cumulative download for a returning user who hits the home screen is still well under fifty kilobytes of new code.

## What you could do better

One real concern I want to flag, and it's a known unknown rather than a guess. The state-machine transition from `needs-identity` to `unlocked` depends on `wallet.holdings()` finding the freshly-created identity attestation. `holdings()` internally calls `loadVerified` on the attestation store, which runs each row through `verifyEnvelope` and only returns the ones that pass. The sign-poisoning fix from the morning means `verifyEnvelope` now uses quorum-of-good — at least one valid signature suffices. A self-signed routine-tier attestation has exactly one signature and that signature is by the wallet's own active key, so verification should pass cleanly. But I want to be explicit: I did not write an integration test that exercises the full `createIdentityAttestation` → `wallet.hold` → `wallet.holdings` → `findIdentity` round-trip. The pieces have unit-level coverage in `tapit-attest` and the registry doctrine has its own tests, but the end-to-end of "create, hold, recover from store, find by subject" is not exercised by anything in this repo. If browser verification surfaces a "I created an identity attestation but the wallet keeps showing me the display-name prompt again" symptom, that's the path to debug first. Adding a vitest integration test for that round-trip is a fifteen-minute follow-up I would do if you ask, but I left it for now because the parts compose from primitives that are each tested, and the operator's time is better spent on browser verification than on my self-doubt.

A second observation, smaller but worth saying. The passphrase-in-`useRef` pattern is correct for a wallet that lives only inside one browser session — the ref clears on sign-out, never crosses a render boundary, never appears in DevTools props, never serializes anywhere. But it does mean that if the user is unlocked and walks away from their phone with the screen still showing, anyone who picks up the phone can hit `/settings` and download an encrypted backup or toggle cloud-sync. The unlock prompt protects against fresh sessions but not against mid-session abandonment. `DESIGN.md §5` calls for an idle timeout — "default thirty minutes, configurable" — which is a Phase Two-and-a-half item rather than a Phase Three blocker. I would either add an idle-timeout hook in the next session before Phase Three, or accept that v1 ships without it and add it pre-launch. Your call.

A third small thing. The local-export download writes the encrypted blob as JSON with two-space indentation — eight hundred and odd bytes of pretty-printed text instead of three hundred-ish bytes compact. The file is ciphertext either way, but the pretty-printing makes the file easier to inspect by eye and slightly larger to store. If you would prefer the smallest possible exported file, I'd switch to `JSON.stringify(blob)` without the indent argument. Both are fine; I picked the slightly larger one because a power user opening their backup and seeing the structure feels less mysterious than a single line of dense JSON. Aesthetic call, easy to flip.

## The bigger picture

The wallet now holds its first signed claim. That sentence sounds small and it is the whole product. Every wallet ever built holds a key; this one holds the chain that grows from the key, and Phase Two is where the chain starts. The identity attestation that lands when the user enters their display name is the first leaf on the root of their attestation tree — the wallet's own claim about itself, "this is me, my name is what I say it is, my pubkey is what it is, and I claim this on the date I claim it." Every future leaf — a third-grade witness attestation, a coach's signature, a medical-license number, a parental birth attestation — sits in the same Merkle field tree and gets signed the same way. The shape is recursive. The wallet you have now can be extended without rewriting because the data model is already general enough to hold everything else. That is the architecture paying off.

The settings surface is where the user's relationship to their own backup posture becomes explicit. `DESIGN.md §6` named three layers — cloud, local export, social recovery — and Phase Two has now made the first two visible and toggleable. The cloud-sync toggle is more than a feature; it's a statement of who the user trusts. Default ON because most users are forgetful and a cloud copy is cheap insurance; flippable OFF because some users want full sovereignty. The local-export button is the disaster-prep card the user squirrels away in their own cloud, their own paper safe, their own encrypted password vault. The two layers compose: even a user who turns cloud off can still survive a lost device if they exported once and kept the file. Layer three — social recovery — is Phase Three's whole job. The substrate it sits on is now ready.

The other thing worth naming is that the wallet is becoming testable as a real artifact rather than as a design. You have not run it yet. When you do, the verification path is short and concrete: create an account, set a passphrase, set a display name, see your identity attestation on the home screen, navigate to Settings, toggle cloud-sync off and watch the banner change, toggle it back on and watch the banner clear, download a local backup file (open it in a text editor, it should be a JSON object with the EncryptedBlob fields), sign out, sign back in via a fresh magic link, enter your passphrase, land on the home screen with your identity attestation still there. If any of those steps surprises you — even a flicker of the wrong screen, even a delay that feels longer than the network warrants — that's the signal that something in this commit needs revisiting. Trust the gates for code correctness; trust the verification walk for feature correctness. The two together are what proves the wallet works.

I am ready to cut Phase Three when you give the word. Social recovery is the hardest piece of the v1 architecture because it composes social engineering with cryptography, and it is also the most distinctive piece — no other wallet does anything like it. If browser verification goes clean on Phases One and Two, Phase Three is the next session and it is where the wallet stops being a personal store and starts being a social one.
