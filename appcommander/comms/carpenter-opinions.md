# Carpenter opinions — 2026-05-25 — Phase A FROST library evaluation

## Section 1 — What I did

The operator opened a session asking for the best way to implement Phase A of the FROST-first quorum and charter-governance roadmap, with a full analysis of each viable path. Phase A is the library cut: vendor a vetted FROST-Secp256k1 implementation into tapit-attest, expose the DKG and signing primitives the rest of the roadmap depends on, and prove RFC 9591 test-vector compliance before any wallet code touches it. The work this session was evaluation, not coding — choosing the library is the gate that has to clear before a single line of Phase A code makes sense to write.

I grounded in the brief at `project-memory/foreman-memory/projects/tapit-wallet/briefs/2026-05-25-frost-first-and-charter-governance-roadmap.md` and read it end to end. I traced the existing tapit-attest layout to understand what shape the new module would take alongside the existing twenty-plus core files and twenty-plus tests, and I read the shamir module and its test file as the closest existing template for "vendored crypto primitive plus RFC vector tests." I checked the bundle-budget script that governs every chunk size in the wallet, because the FROST library is the heaviest single dependency anyone has ever proposed adding and the budget math directly constrains which path is viable. I also surveyed the live npm registry rather than trusting the brief's package names, and that's where the first surprise landed: the brief's `frostlib` candidate doesn't exist on npm under that name, and a January-2026 entrant called `@frosts/secp256k1-tr` has shipped that the brief doesn't mention.

The bigger surprise was an internal contradiction in the operator-locked decisions. Decision number one of the chip session says, in prose, "FROST library: vendored — Use a vetted Rust-via-WASM build of FROST-Secp256k1 (RFC 9591) into tapit-attest. No roll-our-own TypeScript implementation." That names WASM. But the candidate table directly below it lists two pure-TypeScript options alongside the WASM one and labels the choice "Decision deferred to Phase A; if the operator has a strong prior they can lock it now via a follow-up chip question." Both statements can't be true. The honest thing to do was surface the contradiction in plain English in the chat reply and put both interpretations on the chip-form question I'm closing the session with, rather than silently pick one and act on it.

I then laid out four paths with their tradeoffs. Path one is `@cmdcode/frost` version 1.1.4 as a pure-TypeScript dependency — same noble primitive family tapit-attest already trusts, same author universe as the cmdcode MuSig2 library the May 23 brief was looking at, around forty to sixty kilobytes gzipped after tree-shaking, synchronous API, one focused session of work. Path two is the Rust-to-WASM build of zcash's `frost-secp256k1` reference crate — strongest cryptographic provenance with NCC Group's 2023 audit on its name, but a hundred fifty to two hundred fifty kilobytes gzipped minimum (roughly twenty times the entire current login bundle) and a real build-chain story to figure out. Path three is `@frosts/secp256k1-tr`, which I ruled out for being alpha-versioned — sovereign-identity software is not the place for alpha cryptography. Path four is vendoring cmdcode source directly into the tapit-attest tree rather than via npm, which is a sovereignty stance more than a safety improvement. The recommendation if decision number one is firm is Path two. The recommendation if it's reopen-able is Path one. The chip-form question at the close of the session asks the operator to pick.

## Section 2 — What you could do better

The brief contradiction is a real process issue worth naming. When a brief locks a decision in one sentence and reopens it in the next paragraph, the failure mode is that the Carpenter either picks one interpretation arbitrarily or — worse — doesn't notice the contradiction and acts on whichever sentence registered first. A mechanical brief-lint that flagged the co-occurrence of "locked" or "decision" wording with "deferred" or "open" wording in the same section would catch this kind of internal contradiction at brief-write time. That's the mechanism-over-prose principle CLAUDE_ROOT.md non-negotiable five points at, and it's the kind of check that becomes valuable as the brief library grows and operator decisions accumulate.

The brief's bundle-size estimate for the WASM path (one hundred fifty to two hundred fifty kilobytes gzipped) is named in the candidate table but its implications aren't traced through to the bundle-budget script, which today doesn't scan wasm files at all. A WASM path commits us to extending `scripts/bundle-budget.mjs` before the first Phase A commit can pass the build gate, and that extension itself is a non-trivial piece of work (different content-hashed naming pattern for wasm chunks, different stream-handling for gzip on binaries). If the operator picks the WASM path, that becomes a hidden prerequisite the brief doesn't account for in its "1-2 sessions" Phase A estimate. The honest number for Path two is closer to three sessions, not two, once that wasm-bundle-budget extension is factored in.

One more — the brief lists the `frostlib` package as a TypeScript candidate, but no package by that name exists on npm under any of the maintainer hints the brief mentions. The brief is sketch-grade and that's expected, but the live-state correction belongs in any chip-form question I send the operator so he isn't picking from a stale shortlist. I included the live npm-registry corrected list in this session's chat reply for that reason.

## Section 3 — The bigger picture

This session is one of those moments where the wallet's prime directive ("safe beats fast") meets its bundle-discipline doctrine ("the smallest useful thing correctly") in a place where the two directives can pull in opposite directions. The Rust-to-WASM reference implementation is the safe choice in the audit-pedigree sense — it's what NCC Group looked at, what zcash maintains, what custody businesses are betting their balance sheets on. The pure-TypeScript choice is the safe choice in the operational-simplicity sense — it loads synchronously, tree-shakes properly, uses primitives the rest of the wallet already trusts, doesn't require a Rust toolchain in CI, doesn't risk a WASM binary in git becoming a supply-chain hop nobody audits. Both are honest safety arguments. Which one wins depends on whether the operator weighs "an external auditor signed this code" higher than "the code lives in one toolchain we already understand end to end and is small enough to be lazy-loaded into a chunk we can budget mechanically."

What the four-phase shape of the roadmap reveals is that Phase A's library choice cascades through everything after it. The DKG and signing ceremonies in Phase B inherit whatever API shape the chosen library presents. The dual-tier organization creation in Phase C calls into Phase B. The charter validator in Phase D verifies signatures produced by Phase A. A WASM choice means async APIs propagate through every ceremony modal, the inbox routing, and the validator. A TypeScript choice means everything downstream stays synchronous, which is how the rest of tapit-attest is already shaped. So the chip-form lock you're about to make isn't just "which library" — it's "which shape does the entire FROST surface take across the next six to seven weeks of the roadmap." That's why the contradiction in the brief needs resolving now rather than deferred into Phase A's first commit, where the implications would only become visible after work is already underway.

Pick the path that lets the next session start cutting without ambiguity. That's the real deliverable today.
