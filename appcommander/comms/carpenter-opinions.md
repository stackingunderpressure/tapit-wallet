# Carpenter opinions — Phase 5c-i-γ (wiring transport into the wallet)

## Section 1: What I did.

This was the cut where the wire client built last session learned to live inside the wallet without leaking what the wallet is most careful about — the user's private key. The transport feature, as shipped, took raw keys in and out of its public functions. That was fine for a unit-tested library in isolation, but a real wired-up system has to obey D-03, the non-negotiable that the user's keys never leave the wallet unencrypted. So this cut routed the entire peer-encryption and Nostr-event-signing surface through the Wallet object instead.

The first move was adding three methods to the Wallet class in tapit-attest. `signDigest` takes a thirty-two-byte digest and returns a BIP340 Schnorr signature as hex — the wallet uses it for Nostr event ids. `nip44EncryptTo` takes a plaintext and a recipient's x-only public key and returns NIP-44 v2 ciphertext, with this wallet as the sender. `nip44DecryptFrom` takes a payload and a sender's public key and returns the plaintext, throwing on MAC failure. All three thread the wallet's private key from its internal storage to the audited noble primitives without the key ever crossing a method boundary. Each one is a few lines.

The second move was a doctrine upgrade I did not plan to make this cut but had to once the grounding gate caught me. I had written a test asserting that `wallet.keypair` was undefined from outside — meaning a third-party caller could not reach in and grab the keys. The test failed. The reason was instructive: the existing `private keypair: Keypair` declaration was TypeScript-private, which is purely a compile-time check. At JavaScript runtime, `wallet.keypair` was fully accessible. That is a real D-03 hole — a buggy debug log of a Wallet reference, or a malicious dependency evaluated in the same JavaScript context, could enumerate the keypair. The fix was a one-character upgrade: change the field declaration to `#keypair`, the JavaScript private-field syntax, which is a true runtime-enforced encapsulation. The field is unreachable from outside the class, not even by `Object.keys` or `Reflect`. Every internal `this.keypair` became `this.#keypair`. The doctrine line in CLAUDE.md that says "keys never leave the wallet" now has a runtime guarantee underneath it, not just a sentence.

The third move was refactoring the transport feature to consume the new Wallet surface. `buildEvent` in `nostrEvent.ts` used to take a raw private key string; now it takes a `sign` callback — the caller passes `(digest) => wallet.signDigest(digest)` and the function never sees a key. `sendEnvelopeTo` and `subscribeInbox` in `encryptedInbox.ts` used to take pubkey-plus-privkey string pairs; now they take a Wallet. The encryption happens through `wallet.nip44EncryptTo`, the decryption through `wallet.nip44DecryptFrom`, the signing through the callback. The transport feature, end to end, no longer has a parameter typed as a private key.

The fourth move was a small helper, `connectWallet`, in a new file. It is the one-call entry point a UI layer will use. You pass it a wallet and an `onEnvelope` handler. By default it opens a `NostrTransport` against the default relay set; you can also pass an injected Transport for tests. It subscribes the inbox to the wallet's pubkey, returns a handle, and the handle's `close()` tears the whole thing down — closes the subscription and, if the transport was internally created, closes the transport. Two new tests verify the open-deliver-close lifecycle and the clean teardown when the transport is internally owned.

All eight gates green in both packages. The tapit-attest test suite gained six new tests for the Wallet methods — round-trips, third-party rejection, wrong-sender rejection, digest length validation, and the now-passing assertion that `wallet.keypair` is undefined from outside. The wallet test suite gained two new connectWallet tests. Bundle budgets are clean; the tapit-attest vendor bundle grew by a couple kilobytes gzipped to absorb the NIP-44 primitive now being runtime-imported by the Wallet class, well inside its thirty-five-kilobyte budget. Pushed to the working branch as commit `25be3ba`; not pushed to main this turn.

## Section 2: What you could do better.

Three things, in roughly decreasing order of urgency.

The same NIP-44 reference-vector verification I mentioned the last two sessions is still outstanding. The next cut (5c-i-δ) is the one that wires this stuff into the actual user-facing flows, which means it is the cut after which real messages start going to real public relays. The reference vectors should be run through `encryptTo`/`decryptFrom` before that point, not after. It would be a fifteen-minute job — copy the vectors from the NIP-44 spec repo, write a test that round-trips them, run it. Worth doing.

I want to also flag what I did NOT do this cut: I did not wire the transport into `WalletProvider`. I considered it, and decided it crossed a line. The moment `WalletProvider` opens a `NostrTransport` on unlock, every public relay in the default set learns the wallet's pubkey is online — by virtue of the subscription with `#p: [pubkey]`. That is real metadata, real privacy cost, and it should not happen until the operator has explicitly opted in. The right shape is a settings toggle (`nostrTransportEnabled`, default false) that the operator turns on when they want the network active. I deferred that to 5c-i-δ because it is a coherent unit of work by itself: prefs schema change, settings UI, context exposure, plus the wiring. Trying to land it under 5c-i-γ would have blurred the boundary; landing it under 5c-i-δ keeps each cut small enough to reason about. That is a judgment call worth knowing about — not a corner cut.

Smaller observation: when I refactored `buildEvent` to take a `sign` callback, I kept the signature synchronous (`(digest: Uint8Array) => string`). That works for in-process wallets but would not work for a remote-signer scenario like NIP-46, where signing is asynchronous. If the wallet eventually grows a remote-signer surface, the signature needs to become `Promise<string>` and every caller becomes `await`-aware. Not urgent today — there is no remote-signer path in this codebase — but worth knowing when that day comes.

## Section 3: The bigger picture.

The interesting move this cut was not the wiring — it was the encapsulation upgrade that the wiring required. There is a deep pattern in security software: rules that are documented but not enforced get violated. A line in CLAUDE.md that says "keys never leave the wallet" is a vow; a `private` modifier in TypeScript is a vow with a compile-time check; a `#` private field in JavaScript is a vow with a runtime guarantee. Each form has a name on the doctrine wall, but the actual property they ensure is wildly different. The first relies on a person remembering. The second relies on the type-checker running. The third relies on the JavaScript runtime itself — the language closes the door, and nothing can reach through it. That is the mechanism-over-prose principle the chassis already says elsewhere, applied to the most sensitive thing the wallet owns. The grounding-gate hook was what caught the gap; without it, my test would have passed by accident because I was running it under TypeScript and the test happened to also have access to `wallet.keypair`. The gate made me check what the truth was, which made me find that the truth was looser than the docstring. The fix made the docstring true.

The other shape worth seeing is what the wallet now offers as a contract to its own internal modules. Before this cut, the way to sign anything was either through the high-level `attest` and `sign` methods (which sign envelopes, the canonical case) or by reaching into the keypair somehow. Now there is a clean middle layer — `signDigest` for arbitrary thirty-two-byte hashes — that gives the peer-transport layer exactly what it needs without giving it the key. And there is a peer-encryption pair, `nip44EncryptTo` and `nip44DecryptFrom`, that does the same for confidential messaging. The library is growing toward the shape of "everything sensitive happens inside the Wallet object; everything else just asks the Wallet politely." That is the architecture that lets the Wallet eventually become a hardware-backed object — a secure-element-held key, a passkey-protected derivation — without any of the calling code needing to change. The wallet feature builds toward the day when even the in-memory representation of the keypair is gone, and the only thing the Wallet has is a handle into the OS keystore. The interface is ready for that day; the implementation is the part that catches up.

Next session is 5c-i-δ — the cut where this infrastructure finally meets a UI. There will be a settings toggle, a WalletProvider lifecycle, and an inbox surface in the People tab that says "you have one envelope waiting." That is the cut where the operator stops having a wallet that could be a network node, and starts having a wallet that is one.
