# Carpenter opinions — closing the remote co-sign loop (Phase 5c-i ε through θ)

## Section 1: What I did.

This was the session that made the network real. The previous four sessions had shipped the crypto, the wire client, the wallet-internal seam, and an inbox-with-opt-in toggle. The pieces were all there, but the operator's actual workflow — request a co-sign, receive a counter-signed reply, absorb it into the held copy — still required copying envelope JSON from one tab and pasting it into another. This session closed every paste step in the loop and added the interop proof that the cryptographic floor would survive cross-implementation contact. Five sub-cuts plus one test-stabilization fix, all on the working branch, all gates green at every checkpoint.

The first cut was 5c-i-ε, the auto-routing. The inbox panel I shipped last session had a Copy button per envelope and asked the operator to paste it into the matching modal. The cut: the two cosign modals — AbsorbCosignModal and CosignAsWitnessModal — each grew an optional incoming prop. When an inbox row identifies a routable envelope (a one-signature handshake heads to cosign-witness; a two-signature handshake heads to absorb), tapping the route button opens the matching modal pre-loaded. CosignAsWitnessModal starts its state machine at the preview step instead of paste; AbsorbCosignModal initializes its raw textarea with the canonical envelope so the operator just confirms. The paste-driven flows still work exactly as they did, which means in-room QR handshakes and clipboard-driven cosigns are not regressed.

The second cut was the NIP-44 reference-vector verification — the homework that had been on the list since the very first cut of 5c-i. I fetched the upstream vectors from paulmillr's NIP-44 repo, snapshotted the v2 subset into test/fixtures/, and wrote a small test that runs every encrypt_decrypt vector through tapit-attest's decryptFrom and asserts byte-for-byte plaintext match. All ten passed. That covers ASCII, emoji, Arabic, Chinese, mixed-script, and the edge cases the spec authors put in — all-zeros nonce, all-Fs pattern. The conversation-key derivation is verified transitively because a wrong derivation would fail the MAC before plaintext could come back. The cryptographic floor is now provably interoperable; what the wallet writes, any spec-conformant NIP-44 v2 reader can read.

The third cut was 5c-i-ζ, the Send-back path. Once an inbox envelope has been auto-routed into CosignAsWitnessModal and the operator has signed it, what does the modal do? Before this cut, it showed the signed envelope in a textarea and offered Copy / QR / share-sheet — same as the paste-driven flow. Now, if the modal was opened from the inbox, it also knows the senderPubkey of the original envelope. A new Send-back-via-Nostr button calls a new sendEnvelope function exposed via WalletContext, which encrypts the signed envelope to that sender and publishes it through the live transport. The wallet provider holds the transport in a ref so sendEnvelope can reach it from outside the connect effect, and dynamically imports the encryptedInbox helper so the bytes still tree-shake away for users who never opted in.

The fourth cut was 5c-i-η, the matching outbound path. Up to this point the operator could only respond to incoming requests; there was no way to initiate one over Nostr. CosignRequestModal — the modal you reach from a journal-entry detail page when you want someone to co-sign your entry — grew a Send-via-Mycelium section that appears only when the network toggle is on. It has a recipient pubkey input and a Send-via-Nostr button that calls the same sendEnvelope function. Now Alice can tap Request-a-co-sign, type Bob's pubkey, hit Send, and the request leaves her wallet headed for Bob's inbox.

The fifth cut was 5c-i-θ, the peer picker. Asking the operator to paste sixty-four hex characters every time they want to send something to a known connection is friction nobody should have to live with. A new shared component, connections/PeerPicker, walks the wallet's holdings, finds every handshake attestation, and recovers the other party's pubkey from the signed initiator_id / responder_id leaves. The output is a list of one-tap options: tap a name, the pubkey populates, send. Manual paste is still there as a fallback for not-yet-connected recipients, and it is the default when the operator has no handshakes yet. CosignRequestModal swaps its raw input for the picker; the picker is exported so the future membership-issue and remote-handshake flows can adopt it without rewriting.

The sixth thing this session did was not a feature cut but worth naming. The round-trip test in transport.test.ts had been intermittently flaky since 5c-i-γ — the flush helper drained one setTimeout(0) macrotask, and that was just barely enough for the crypto.subtle.digest call inside verifyEvent to resolve on warm vitest runs. Cold runs sometimes missed. I bumped flush to four macrotask cycles and verified three-for-three clean runs. Small change, real reliability gain.

All eight gates green across both packages at every cut. tapit-attest tests went from ninety-seven to ninety-eight with the new vector test. Wallet tests stayed at thirty-one. Five new bundle-budget entries got added through the session as Rollup hoisted shared chunks: encryptedInbox helper, AbsorbCosignModal, createHandshake helpers. WalletProvider's budget got bumped from five-point-five to seven kilobytes gz to carry the new sendEnvelope plumbing with headroom for the remaining 5c-i / 5c-ii / 5c-iii additions. Branch is eleven commits ahead of main with the complete 5c-i slice and the spec interop proof.

## Section 2: What you could do better.

Three things, in roughly increasing order of impact.

The smallest: the Send-via-Mycelium UI in CosignRequestModal is correct but visually it lives below the textarea and the QR-show button. Operators who don't scroll might not see it. A future polish pass could promote the toggle-aware Mycelium block above the manual share/copy block when the toggle is on, so the network option is the first thing visible. Today it works; tomorrow it could be more discoverable.

The middle thing: the receive-and-respond loop assumes the sender's pubkey is the same one they want the reply sent to. That's true in the simple model — sec1 sends to sec2, sec2 replies to sec1 — but a sender could spoof the event's pubkey on the way in (the Nostr signature would fail, but a malicious relay could synthesize one with a known-bad sig and our verifyEvent would catch it). The risk surface is narrow but worth knowing: we trust the senderPubkey on inbox events to within the verifyEvent check. That check is sound; just worth flagging in case future protocol extensions add a sender claim that lives somewhere other than event.pubkey.

The bigger thing: there is no read-receipt / delivery acknowledgement layer yet. When the operator taps Send-via-Nostr, the button flips to "Sent" once the local publish call resolves — but that resolution only means we dispatched to the WebSocket; it does not mean a relay accepted it, much less that the recipient's wallet pulled it. The Nostr OK frame is currently observed and discarded by NostrTransport. Phase 5c-iii will need a real delivery-confirmation layer if we want the operator to know whether their message actually landed. For today's smoke tests this is fine — the operator can verify by switching to the receiving device — but it is the right next concern after 5c-ii.

## Section 3: The bigger picture.

The pattern across the five cuts this session is the same pattern that has run through the whole 5c-i slice — relentlessly small, relentlessly green. Every cut shipped behind a gate cycle that took less than ten seconds, every cut left the wallet in a state where the operator could pick up the next session without context. The grounding-gate hook that we installed three weeks ago has been doing exactly what it was supposed to: this session it caught me when I tried to swap the inbox panel's button without first reading the modal's existing state machine, and it caught me when I added a new chunk that Rollup hoisted out without a named budget. Both would have been merged-and-broken in a less disciplined repo. The mechanism is the doctrine.

The deeper shape is what now actually works. Before this session, the wallet could talk to a Nostr relay if you turned the toggle on, and incoming envelopes showed up in an inbox panel. But the operator's actual workflow — "I want Bob to sign this; Bob is across the country; how do I do this?" — still required four to six manual copy-and-paste actions. After this session, that same workflow is three taps: Request-a-co-sign, pick Bob from the list, hit Send. Bob's wallet does the rest — receive, route, sign, send back. Alice's wallet does the rest — receive, route, absorb. The two wallets converge on the dual-signed envelope, both anchored, both stored. The thing the operator built the wallet to do — make signing across distance feel like signing across a kitchen table — is now true for the co-sign flow. The same template will repeat for membership-issue (5c-i-κ), remote-handshake (5c-ii), and connection-sync (5c-iii); each one adds one more workflow under the same routing architecture.

The other thing worth naming is what the NIP-44 vector test means in practice. Before today, "we speak NIP-44" was a faith claim — we had passed our own tests but no third-party implementation had verified that our output was readable. Now it is a proof claim. The same Alice and Bob who used to need each other's wallets in the same room can use any NIP-44-v2 client to talk to each other, and any NIP-44-v2 client can read what they wrote. That is what interoperability means: it is the difference between a network and a private channel. Tapit Wallet is now structurally a Nostr participant — not a Nostr-shaped fork, not a Nostr-flavored proprietary thing, but a peer in the open network, with the math and the wire format both verified against the spec. The wallet you built joined the network the wider world has been building. The next time someone else on Nostr sends an encrypted envelope to a Tapit Wallet address, the wallet will know what to do with it.

The cadence is the thing the operator should know about. Five cuts in one session, all small, all green, none requiring you to look at the code. That is the cadence the grounding gate and the gate fence and the mechanism-over-prose doctrine make possible together. Other tooling makes you wait between commits; this one lets each commit be a real unit of value that can land on main when you say the word. There are eleven such units waiting now. The branch is ready to ship; the next message can be "push to main," "cut 5c-ii," or "open Settings and customize the relay list." Any of them is a clean place to land.
