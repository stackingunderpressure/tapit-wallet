The second cut was `9989bc0` — Phase 8 Phase E1 from the open-joining brief. This is the substrate that opens the entire membership-acquisition axis of the org-governance roadmap. The existing `AuthRule` type covered only signer-side rules — actions the organization itself takes, with a threshold of signatures required from an eligible set. The open-joining brief specifies a joiner-side rule for member-initiated joining, with a `policy` payload instead of `{threshold, eligible}` because the joiner isn't proving signatures from an authorized set; they're claiming membership and the org's declared join-policy decides whether the claim is valid. I made `AuthRule` a discriminated union of `AuthRuleForOrgAction` (the existing shape, preserved structurally so pre-E1 declarations decode identically) and `AuthRuleForJoin` (`{action: 'join', policy: JoinPolicy}` where `JoinPolicy` is itself a six-kind discriminated union: open, allow_list, deny_list, requires_handshake, requires_credential, requires_vouch). Dispatch happens by action name in `encodeAuthRuleValue`, `decodeAuthRuleValue`, and `buildAuthSubtree` so the on-disk canonical-JSON encoding stays backward-compatible. Type guards `isOrgActionRule` and `isJoinRule` let consumers narrow safely.

The narrowing cascade was the part I treated most carefully because three existing consumers read `rule.threshold` and `rule.eligible` directly and would no longer typecheck once the return type became the union. I tightened `defaultAuthRules`'s return type to `AuthRuleForOrgAction[]` (it never returns join rules — it's the founder-signs-everything fallback), which cascaded cleanly into `SettingsScreen`'s `orgRules` state and `OrgRulesEditor`'s `value` and `onChange` prop types both tightening to `AuthRuleForOrgAction`, reflecting the editor's actual scope. `MembershipModal`'s issuance-rule useMemo refuses to bake `authorized_by` if the `routine_issuance` leaf isn't org-action shape; `CosignRequestModal`'s `orgRule` useMemo falls back to the general `PeerPicker` when handed a join-action context (the modal is signer-side only); `verifyOrgAuthorization` in `createOrganization.ts` returns `authorized: false` with an honest "not a signer-side org-action rule" reason when the disclosed leaf is a join rule. The joiner-side verifier ships in Phase E4 as a separate primitive. A new test file `src/features/governance/authRule.test.ts` ships 22 tests covering each of the six `JoinPolicy` kinds round-tripping encode-to-decode unchanged, pubkey lists getting sorted-and-lowercased inside the policy payload exactly the way org-action eligible lists already do, decode rejecting malformed payloads, `buildAuthSubtree` accepting a mixed rule set, and backward compat for pre-E1 leaf values. ## Section 3: The bigger picture

What this session opened up is structurally distinct from everything that came before in the Phase 8 arc. Phases A through D of the canonical Tapscript-style brief are all about the org's signer-side authorization — what the organization itself does, who's authorized to sign for which action, how those rules amend over time, how the verifier confirms an org's action was authorized under its declared rules. That's the org-control axis. Phase E1 just opened a perpendicular axis — the membership-acquisition axis — where the question flips from "who signed?" to "who's allowed to join?" The same Merkle-tree-of-leaves substrate the wallet has used since Phase 4 for selective disclosure of facts now also encodes joiner-side abuse-resistance policy alongside the signer-side multisig rules, all in the same `auth` sub-branch, all proved via the same `disclosureProof` primitive. Zero new cryptography. The substrate compounds.

The structural lesson here is the one the wallet has been quietly teaching across the whole codebase: when you build the right primitive once, the next ten features that come along all extend the primitive in place rather than reinventing their own. The disclosure-proof primitive shipped for "prove you're over 21 without revealing your birthday" turned out to be the same shape as "prove the org's auth tree commits to this rule without revealing the other rules" which turned out to be the same shape as "prove the org's join policy accepts this membership without revealing the rest of the policy alternatives." Three different product surfaces, one cryptographic primitive, identical verification path. That's what makes the leaves theory load-bearing across credentials and organizations and probably whatever agreements-and-predictions surface comes next.

The dispatched-session protocol's structural-not-buggy framing you corrected me on mid-session is worth dwelling on for a sentence. Direct-to-main from a sandboxed carpenter would route work around the operator's review surface — they couldn't see what they were merging, couldn't unmerge cleanly via the cockpit, couldn't compose multi-cut sessions into a single review unit. Branch isolation makes the cockpit's merge button the single chokepoint for what enters main, which is exactly the integrity property an operator running on iPhone needs from a multi-agent dispatch fleet. The "lnuckle head" correction was generous teaching — the actual lesson was that "stale" was the wrong word because it implied something was broken when in fact something was working precisely as designed. Carpenters reading this letter benefit from knowing the framing matters: the SessionStart-injected handoff from origin/main reflects what's been MERGED, not what's been SHIPPED, and that distinction is the whole reason the cockpit exists.
