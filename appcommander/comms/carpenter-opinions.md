The check lives in a new `src/library-seam.test.ts`. It walks every `.ts` and `.tsx` file under `src/features` (excluding test files), extracts function definitions, class definitions, and `const`-arrow-or-function assignments via three regex patterns, and fails the test if any of those names overlaps a runtime export of `tapit-attest`. The runtime export list comes from `Object.keys` of the wildcard import — TypeScript types are erased at runtime, so the keys list contains only the value exports (the actual functions, classes, and constants the wallet could accidentally collide with). An `ALLOWLIST` exists in the test for intentional name coincidences but it's currently empty by design — every existing wallet name is distinct from the library's public surface, which is the property the check exists to preserve. The check runs in about thirteen milliseconds and lives alongside the existing `persona-contract` and `features-registry` tests in the `npm test` suite, so it fires on every gate cycle.

The "don't trust, verify" framing applied to the check itself. I didn't just write the test and call it done because it passed on clean code — passing on clean code only proves it doesn't false-positive, not that it actually catches what it claims to catch. So I deliberately injected a canary: a one-line file at `src/features/journal/__canary.ts` exporting `function envelopeId(): string` — a name that's already exported by `tapit-attest`. Ran the test. It failed loudly with the exact file path, the exact colliding name, and a helpful error message pointing the next Carpenter at `ALLOWLIST` as the fix path. Removed the canary, re-ran, back to seventeen of seventeen tests passing. The check is mechanically verified to detect the bug class it exists to detect. ## What you could do better

One real limitation worth flagging. The check catches *name* collisions — when a Carpenter accidentally writes `function envelopeId(...)` in wallet code, the test fires. It does NOT catch *semantic* collisions — if a Carpenter writes `function computeContentAddress(att) { ... }` that re-implements `envelopeId` under a different name, the test would not notice. That's the rarer failure mode and the verbal diff-review still has to catch it, but I want you to know the scope. The mechanical check handles the dominant case (the three bugs from this week's blocks were all name collisions or near-name-collisions); the remaining cases need eyes on the diff. If semantic-collision bugs start to recur, the next refinement would be a heuristic check that flags any wallet function whose body imports `taggedHash`, `concatBytes`, or other library-internal building blocks — those are the load-bearing primitives a re-implementation would use, and they're not in the library's public surface so a flag there would be a strong signal.

The other thing worth mentioning is that the test file lives at `src/library-seam.test.ts`, alongside `src/features-registry.test.ts` and `src/shared/persona-contract.test.ts`. That's three top-level test files in `src/`, which is starting to look like a pattern. If a fourth doctrine-mechanism test lands, I'd hoist them into `src/doctrine-tests/` or similar so the surface stays tidy. Not urgent now; flagging the trend.
