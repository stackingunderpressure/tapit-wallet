ShareCard.tsx is pure presentation. QuickShareModal.tsx is the bridge between the catalog and the card. It mints the multi-disclosure proof bundle for the preset's leaves once via useMemo, base64url-encodes the bundle, and computes the verifier URL. When the encoded URL fits under an 1800-byte cap — chosen because iMessage preview generation and some QR limits prefer shorter URLs — the card carries an inline /verify?p=<bundle> link so the verifier taps once and the math runs automatically. When the encoded bundle is bigger than the cap, the card falls back to a plain /verify URL and the modal subtitle adjusts to say "send it alongside the proof JSON below" so the operator understands they need to attach the bundle separately. The modal exposes a system Share button (Web Share API where supported, clipboard fallback otherwise), a Copy link button, and a Show proof JSON expandable for operators who want to see what is actually being disclosed. Share-card-modal styling mirrors the FreshLoginShell — black/60 backdrop blur, fresh-surface-raised body, fresh-accent-primary primary button, motion-reduce respected.

The verifier route earned a small additive feature to close the one-tap loop. VerifyProofScreen now reads the ?p query parameter on mount, base64url-decodes it, pastes the result into the textarea so the operator can see exactly what was verified, and runs the verifier. The previous verify() function was refactored into verifyText(text) that takes the proof text as input plus a thin wrapper that calls it with the textarea state — both the URL-param path and the paste path share one verifier code path so the green-or-red panel behaves identically. Decode failures surface as a friendly "the verify link is malformed — paste the proof manually" message in the same Outcome surface a JSON parse error would, so the verifier never sees a crash.

## Section 2: What you could do better.

The biggest substantive observation is the inline-verify URL size cap. I set it to 1800 bytes empirically because iMessage previews and QR-code generators prefer shorter URLs, but the real threshold varies — Twitter has a different limit than iMessage which has a different limit than the WhatsApp link preview engine which has a different limit again than what fits in a SMS body. The current behaviour falls back gracefully to "paste the JSON separately" when the inline URL exceeds the cap, but you may want to tune the cap up or down once you see how operators actually share — if the inline path is what makes screenshots work, lift the cap; if it surfaces ugly long URLs in chat previews, drop it. The constant lives at the top of QuickShareModal.tsx and is easy to adjust.

A second observation about the share card's visual treatment. I built the card on the existing fresh-aurora-bg background helper because that is the established Fresh aesthetic and reusing the helper keeps the CSS bundle tight, but a screenshot-targeted card is fundamentally different from an in-app surface — the aurora drift animation does nothing in a static screenshot, and the background gradient eats into the gravity the assertion line should own. A future polish pass might give the share card its own purpose-built background — a more saturated gradient, less aurora movement, more product weight. For now the visual is consistent with the rest of the Fresh surface which is the right call for a first ship, but you should know the screenshot-target use case may warrant a custom backdrop later.

Third, the membership preset surface. Today I list one preset per held membership credential, labeled "I belong to {orgName}". This is honest and works, but if the operator holds memberships in twelve organizations the Quick-share section becomes a long scroll. The natural follow-up is grouping — "I am a member of {orgName} (3 more)" — or filtering by most-recent or by org-categorized tags. For one or two memberships the current list is fine; for the audience the brief targets, who may belong to gyms and clubs and concert membership programs, the list could grow fast. A simple "show top 3, see all →" pattern would handle that gracefully and keep the section visually tight.

Fourth, the ShareProofModal "View as share card" hook routes through QuickShareModal with an ad hoc preset built on the fly. This works but the adhoc preset's label reads "Proof from this {kind}" which is uninspiring compared to the deliberate "I belong to {orgName}" or "I have a verified profile" labels the catalog produces. If the operator uses the manual-leaf-pick flow under Fresh, the share card looks slightly less editorial. A future cut could let the operator type a custom assertion line on the way to the share card so their manually-picked proofs get the same headline weight as the presets.

Fifth, and this is more of an architectural note than a flaw — the inline verify URL pathway commits to a specific encoding choice. If we later decide to switch from JSON-base64url to a more compact serialization (CBOR with base32 for example), every share card minted under the current format will need both the new verifier to accept the old format AND a code path that recognises which format a given ?p= parameter uses. The current decodeInlineProof helper is small enough that a v2 marker prefix would be cheap to add at any time; just flagging that the format is now part of the wire surface the verifier route maintains.

## Section 3: The bigger picture.

What you actually shipped in this cut, beneath the visible share card, is the wallet's first answer to a different but adjacent architectural question — at what moment does the audience the brief targets actually distribute proof of who they are. Sovereignty as a value proposition does not spread because someone reads a white paper about it. It spreads because someone screenshots a one-tap credential that worked at a door or at a club or at a friend's birthday, and the receiver taps the link and watches the math validate in green without anyone trusting any platform in the chain. The compose-first onboarding from Cut 5 argued that the operator's life is the substrate. The share card from Cut 7 argues that the operator's reputation is propagatable — that the audience can hand pieces of their verified self to one another the same way they hand each other photos and memes and concert tickets, except these pieces verify themselves.

The technical shape this cut leaves the codebase in is also worth noticing. The selective-disclosure primitive that lived inside ShareProofModal as a checkbox-pick-and-paste-the-JSON flow now has three honest surfaces — the existing manual picker for power users, the Quick-share preset catalog for one-tap common cases, and the share-card visual treatment for screenshot distribution. All three render through the same multi-disclosure proof bundle, all three flow through the same verifier route, and the verifier route now accepts both pasted JSON and inline URL parameters — one bundle shape, three operator-facing entry points, two ingestion paths. The architecture compounds: every future preset, every future visual treatment, every future verifier ingestion mode plugs into the same pipeline without changing the cryptographic core. That is the boring leverage the wallet earns by keeping the math primitives behind a single library and treating presentation as the layer that varies.
