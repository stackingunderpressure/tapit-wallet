# Carpenter opinions — Phase C cut 3 caller-wiring (2026-05-26 early morning)

## Section 1: What I did

One commit landed on the dispatch branch this session, and it was the natural close-out of the Phase C arc. The prior carpenter's letter named caller-wiring for the new `CosignRequestModal` `orgContext` mode as the recommended first move, and the operator's prompt was the open invitation to take the largest safe chunk, so I treated that as the unit of work and cut the whole loop end-to-end in one commit. The cut had two parts that depend on each other. First, `buildMembershipDraft` in `createMembership.ts` gained an optional `authorizedBy` parameter that bakes a top-level `authorized_by` leaf into the membership envelope at draft time. The leaf carries the disclosure proof of the org's `routine_issuance` rule from the self-declaration's auth tree, and because it lands inside the envelope's claim tree before signing, the org's signature covers it — a downstream attacker cannot detach the proof, swap in a different one, and present the new combination as still-signed. The back-compat path is clean: omit the parameter and the draft falls back to the original five-field membership shape, which keeps pre-Phase-8 orgs untouched and stays honest about what's actually been authorized.

Second, `MembershipModal` became the caller that constructs the payload. The modal now reads the operator's holdings, finds the operator's own org self-declaration via `findOwnOrgDeclaration`, looks up the `routine_issuance` rule via `findAuthRule`, builds the `AuthorizedByPayload` via `buildAuthorizedByPayload`, and threads it through `buildMembershipDraft` in the existing `onScanIdentity` path right before `wallet.sign`. If the operator isn't an org, or their org's self-declaration predates Phase A and carries no auth tree, the payload comes out null and the draft falls through to the back-compat path — the modal degrades silently to the pre-Phase-8 behavior rather than refusing to issue. When the rule's threshold is greater than one (multi-sig orgs), the issue-show step now renders an amber banner under the QR that names the rule, shows "your signature is one of N required from M eligible", and exposes a "Request co-signs from eligible signers" button. The button opens a lazy-loaded `CosignRequestModal` with `orgContext={orgSelfDecl, action: 'routine_issuance'}` — the same lazy chunk that `JournalDetail` and `PromoteRouter` already share, so no static-import bloat hit the HomeScreen chunk. I checked the bundle budget after the build and HomeScreen rode in at its existing 18.5KB budget with room to spare.

The substrate validation was the part I treated most carefully. I added `createMembership.test.ts` with four round-trip tests that exercise the full producer-verifier loop. The first is the back-compat case — call `buildMembershipDraft` without an `authorizedBy` payload, sign with a raw Wallet, confirm `isMembership` returns true and the envelope has no `authorized_by` leaf. The second is the threshold-one happy path — org self-declares with `routine_issuance` threshold 1 eligible founder, signs a membership with the payload baked in, and `verifyOrgAuthorization` returns `authorized: true` with `eligibleCount: 1, thresholdRequired: 1`. The third is the multi-sig refusal — threshold 2 eligible `[founder, officerB]`, founder signs alone, and the verifier returns `authorized: false` with the reason containing "threshold not met". The fourth is the multi-sig acceptance — same setup, but `officerB.sign` is layered on top of `org.sign` so the envelope carries two distinct signatures from the eligible set, and the verifier returns `authorized: true` with `eligibleCount: 2`. That fourth test is the one that proves the closed loop works under genuine multi-sig conditions, not just the trivial single-eligible case.

All four gates ran green throughout the session: typecheck clean, eslint clean, 140 of 140 tests passing (four new ones), build clean in roughly 3.3 seconds, bundle-budget audit OK across every named chunk with no bumps required. `PLAN.md` Phase 8 Phase C bullet is now marked `[DONE 2026-05-26]` with a one-paragraph rollup of cuts 1, 2, and 3 plus an explicit note that the deferred `RulesEditorModal` belongs to Phase D's charter-amendment substrate. ## Section 2: What you could do better

The `MembershipModal` currently hard-codes `'routine_issuance'` as the only action it issues memberships under — it's a constant at the top of the file named `ROUTINE_ISSUANCE`. That works for v1 because the canonical brief says routine issuance is the only issuance-capable rule until Phase D adds explicit per-action chips, but if an operator declares a multi-rule org and tries to issue a membership under a different rule name (say `expulsion` or a custom action they invented), the modal silently issues under `routine_issuance` without surfacing that they chose nothing. The comment I left in the file is honest about this, but a future cut should add a chip-form action picker on the issue-scan step when the operator's org has more than one issuance-capable rule. Logging it here so the next carpenter doesn't reverse-engineer it.

## Section 3: The bigger picture

What the wallet now does end-to-end is what the canonical Tapscript-style brief promised four phases ago. An operator opens Settings, declares their wallet as an organization with a custom set of authorization rules, lists their eligible signers per rule, sets per-action thresholds, and signs one attestation that commits to the full auth tree as a Merkle commitment in their self-declaration's claim subtree. Later that same operator opens Connections, scans a recipient's identity QR, and the wallet bakes a disclosure proof of the `routine_issuance` rule into the membership it issues — the proof rides inside the signature's coverage so it's tamper-evident. If the rule's threshold is one, the membership is ready as soon as the org signs it. If the threshold is two or more, the amber banner appears, the operator taps "Request co-signs", and the cosign-request modal opens with the rule's eligible signers as a one-tap picker, the action and threshold named explicitly, and the constrained recipient list replaces the general PeerPicker so the operator can't accidentally request a co-sign from someone outside the eligible set. Every step has a human-legible surface and the cryptographic substrate underneath is doing exactly what Bitcoin Taproot's script-path multisig does — reveal one Tapscript leaf from a Merkle tree of alternative authorization conditions — except the leaves are attestation-shaped rather than Bitcoin-script-shaped and the verification happens off-chain by the recipient's wallet running `verifyDisclosureProof`. Zero new cryptographic code in the entire arc.

The structural thing worth noticing is that this whole feature was built on a primitive that was already in production for selective disclosure of facts. The wallet has been able to prove "I'm over 21 without revealing my birthday" since Phase 4 shipped — that was disclosure of one leaf from a Merkle tree of personal facts. The Phase 8 arc generalizes the same primitive to disclosure of one authorization rule from a Merkle tree of org governance alternatives. The shape is identical at the cryptography layer; only the leaf semantics change. That's the kind of substrate reuse that compounds, because every future feature that needs "prove one thing from a set of things without revealing the others" gets the same primitive for free, with the same verification surface and the same anchoring story. The wallet's leaves theory turns out to be load-bearing across credentials, organizations, and probably whatever comes next in the agreements and predictions space.
