## What I did

You greenlit the sign-poisoning fix and told me to keep going until I judged we had enough to start Phase 1 code. I started with the fix. The bug was sitting in `tapit-attest/src/core/keys.ts` at the bottom of the file in `verifyEnvelope` — the function that walks every signature on an attestation and reports whether the envelope is genuine. The old implementation returned valid as false the moment any signature failed, which sounds correct until you imagine a relayer in the middle of the network appending a single junk signature to a genuine envelope as it passes through. Under the old rule that one junk byte poisons the entire envelope; everyone downstream sees a perfectly good attestation reject as invalid. The wallet's whole "math, not trust" promise breaks in that scenario, because the attacker did not need to forge anything, they just needed to make noise. The fix switches to quorum-of-good semantics: the envelope is valid if at least one signature verifies, and invalid signatures are still reported in the errors array and on their `SignerResult` row so a caller can warn the user, but they no longer flip the overall valid flag. I also handled the duplicate-row edge case where an attacker submits a bad signature claiming to be from a signer who already has a good signature on the envelope — the old behaviour would have surfaced that as an error for the same signer who is also reported as valid, which is confusing and gives an attacker leverage. The new code deduplicates: if a signer has any valid row, their bad rows are dropped from errors entirely.

I added two regression tests in `tapit-attest/test/keys.test.mjs`. The first reproduces the exact attack: sign an envelope with a real key, then construct a poisoned envelope by appending a fake signature claiming to come from a second, unrelated pubkey, then verify and assert that the envelope is still valid, the real signer is reported valid, the fake signer is reported invalid, and the errors array names the fake signer. The second test covers the duplicate-row case: sign with a real key, then append a bogus signature row claiming to come from the same signer, then verify and assert that valid is still true and the errors array is empty. Both tests pass. I also audited every caller of `verifyEnvelope` in the wallet's bundled library — `sync.ts`, `weighting.ts`, `revocation.ts`, `recovery.ts`, and `wallet.ts` at lines one-thirty-three and two-twenty-two — and confirmed that the new quorum-of-good semantics is what each one already wants. None of them break, all of them get safer.

After the fix I bumped `tapit-attest/package.json` from `0.1.0` to `0.1.1-wallet.0` per `DESIGN.md` section eleven, which named that version-bump as the way to mark the wallet's bundled library as a forked copy carrying a wallet-side patch. Anyone later doing a fresh upstream pull will see the non-upstream version string and know to merge their changes onto this fork rather than silently overwriting the fix. Three of the four gates ran green on tapit-attest — typecheck, lint, and build. Tests ran seventy-four of seventy-eight passing. The four failures are baseline; they predate this change and I confirmed it by stashing my work and running the suite. They are all in `ots-codec.test.mjs` parsing the file at `test/fixtures/authorship-record.ots`. That fixture is UTF-8-corrupted at rest: the bytes that should be `0xbf 0x89 0xe2 0xe8 0x84 0xe8 0x92 0x94` got rewritten as runs of the UTF-8 replacement character `0xef 0xbf 0xbd`, almost certainly when the binary file was uploaded through a web interface during the original bootstrap. The fixture needs to be restored from the source-of-truth elsewhere and re-committed as a binary blob without any text-encoding pass over it. That is a separate-session task; I did not chase it because you asked me to keep momentum toward Phase 1, not to debug a fixture.

## The bigger picture

The thing that made this session feel like a one-paragraph piece of work even though it's two commits and a judgement call is that the wallet has now stopped being a design conversation and started being a piece of running code, in the smallest possible way. There is one line of working defensive cryptography in the repository that did not exist eight hours ago, and it closes off an entire class of attacks that the system would otherwise have been vulnerable to from day one. That is the smallest possible useful version of correctness done right, and it is the model for every subsequent session: surface one specific harm the system was vulnerable to, write the minimum code that closes it, add a test that proves the harm has been closed, audit the callers, commit, push, move on. If every Phase 1 through Phase 6 session looks like this one, the wallet ships clean.

The reframe from this morning — identity is the chain, not the key — gets its first concrete vindication from the fix that just landed. The reason that reframe matters is that it changes what the network is doing when it verifies an envelope: it is not checking whether a single trusted party signed something, it is checking whether the chain of attestations the user holds is consistent with the network's view of them. Quorum-of-good is the verification rule that fits that worldview, because identity has always lived in the redundancy of signatures rather than in the integrity of a single one. The old all-or-nothing rule was a holdover from a worldview where one signature equals one identity equals one source of truth. The new rule treats every signature as evidence and asks whether the evidence on net is consistent. That is the same shift you made on the design side this morning, just expressed in one function in one file. The architecture is starting to be self-consistent across all its levels.

My judgement on whether we have enough to start Phase 1 code is yes, and the reason is that the planning surface has already done its work. `DESIGN.md` answers the questions that would otherwise stall the next Carpenter session — what the auth flow looks like, what the key generation flow looks like, what the encrypted snapshot is stored as, where it lives, what the home screen renders. `DISCOVERY.md` answers the data-model questions. The library is patched. The version is marked. The remaining unknowns — N-of-M defaults, the verifier surface choice, the idle timeout — are explicitly tagged in `DESIGN.md` section twelve as questions to revisit when they bite, not blockers for Phase 1. Cutting Phase 1 from here is straightforward Carpentry: scaffold the Vite project at the repo root, install dependencies including `tapit-attest` as a `file:` reference, wire `@supabase/supabase-js` for the magic-link flow, build the first home screen, prompt for a passphrase on first login, call `generateKeypair()`, encrypt the snapshot, persist it to IndexedDB and Supabase. One session, possibly stretching to one-and-a-quarter if the Supabase project provisioning has to be scripted. Greenlight that and I will cut it next.
