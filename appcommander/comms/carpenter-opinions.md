## What I did

You said cut away, verify and justify every change, continue adding guardrails. I re-grounded in `CLAUDE_ROOT.md`, and the gate fence section plus non-negotiable five — mechanism over prose — pointed at exactly two rules that the doctrine names as mattering enough to enforce but that had no mechanical check. I cut both. Branch and main are at `75033ec`, working tree clean, every gate green.

The first guardrail is the file-size limit at commit `57e32bc`. `CLAUDE_ROOT.md` lines eighty-three and eighty-four say "Files over 400 lines warn, over 800 error." That rule has been holding by attention — the largest wallet source file is `WalletProvider.tsx` at two hundred seventy-three lines, comfortably under — but nothing enforced it. A new `src/file-size.test.ts` walks every wallet source file under `src/`, excludes test files and ambient type declarations, counts total lines, and applies the doctrine's two tiers literally: a file over four hundred lines triggers a `console.warn` that shows in the test output but does not fail the run, because a file that size is a smell rather than a failure; a file over eight hundred lines fails the test, because the doctrine says a file that large is a feature that needs splitting and the failure message says to extract components, hooks, or service modules.

The second guardrail is the one that mattered most, at commit `75033ec`: the keys-never-leave check. This is non-negotiable number one in `CLAUDE_ROOT.md` — "The user's keys never leave the wallet unencrypted ... This rule outranks every other rule in this file" — and the gate fence explicitly names a "keys-never-leave audit" as a rule worth enforcing. Until this commit, the single most important rule in the entire wallet had no mechanical check. It was held entirely by the Carpenter remembering to look. A new `src/keys-never-leave.test.ts` greps every wallet source file line by line for two hard-fail patterns. The first is a `console` call — log, warn, error, info, debug, or trace — that passes a secret-named identifier: `privateKey`, `passphrase`, `seed`, `mnemonic`, or `secretKey`. That is the dominant leak vector in practice: a developer adds a debug log during development and ships it. The second is a `localStorage` or `sessionStorage` `setItem` call passing one of those identifiers — web storage is plaintext and survives the session, so the passphrase and the private key must never land there. The regexes are bounded by a semicolon so a match cannot span statements, and they are tuned for low false positives: the wallet's existing `console.warn` diagnostics, the ones that pass only a string and an Error object when a remote save fails, do not trip the check, which I confirmed on the clean baseline run.

I was honest in the check's own header about two things it does NOT catch, so they are documented gaps rather than silent ones. It does not catch "transmits" — a fetch or Supabase call that puts a raw secret on the wire — because that is hard to mechanize without heavy false positives; instead that vector is structurally prevented by the storage-layer design, where every byte that reaches the network goes through `tapit-attest`'s `encrypt()` first and the `EncryptedBlob` is the only shape `walletStore`, `remoteStore`, and `remoteMediaStore` ever send. And it does not catch indirect object leaks — `console.log(wallet)` where the Wallet object transitively holds the keypair — because the by-name regex cannot see the word "wallet." The by-object case still needs eyes on the diff. The check is a strong net for the common case, not a proof of absence.

Both guardrails got the verify-don't-trust treatment applied to the check itself, the same way the library-seam audit and the bundle-budget assertion did. For file-size I temporarily lowered the eight-hundred-line error threshold to two hundred, ran the suite, and watched the test fail correctly with `WalletProvider.tsx` at two hundred seventy-three lines tripping the lowered bar, then restored to eight hundred. For keys-never-leave I backed up `createJournalEntry.ts`, injected a `console.log("debug passphrase", passphrase)` into it, ran the suite, and watched the keys-never-leave test fail correctly — naming the exact file, line sixty-four, the kind "console," and the offending line text — then restored the file byte-identical from the backup, confirmed via grep that zero `console.log` calls remained, and re-ran all four gates green at nineteen of nineteen tests. Both mechanisms are confirmed to fail when they should.

## What you could do better

The honest observation is that with these two cuts, the gate fence is now mechanically enforced end to end, and that means the guardrail-adding work has a natural stopping point I want to name rather than blow past. The gate fence in `CLAUDE_ROOT.md` lists five rules that matter enough to enforce: the four base gates (typecheck, lint, test, build), the keys-never-leave audit, the `tapit-attest` integrity rule, the feature-manifest coverage test, and the branch gate. As of this session, the keys-never-leave audit is mechanical, the `tapit-attest` integrity rule has been mechanical since the library-seam audit, the manifest coverage test has been mechanical since `features-registry.test.ts`, and the base gates are the base gates. The fifth, the branch gate — "no unfinished or dead branch before new work" — is explicitly a SessionStart hook concern, not a vitest test, so it lives in a different layer. Every named rule is covered. Continuing to manufacture guardrails past this point would mean inventing checks for rules the doctrine does not explicitly name, and non-negotiable three warns specifically against "no abstraction the task did not ask for." A guardrail for a rule nobody is breaking is cruft. So I stopped at two, both doctrine-named, both verified.

There are two lower-value candidates I want to put in front of you rather than autonomously cut, because they are real but not doctrine-named-as-must-enforce. The first is a total-post-auth-bytes ceiling: the bundle-budget mechanism from the previous session checks each chunk against a per-chunk budget, but it does not catch a death-by-a-thousand-cuts scenario where every chunk creeps toward its ceiling at once and the total post-auth download balloons without any single chunk failing. A check that sums every lazy chunk and compares against one number would close that. The second is manifest `touches`-array accuracy: a feature's manifest lists every file it touches, but nothing verifies the list is current. I would lean against the second one — it would fire on every file add or remove and create constant friction, and stale documentation in a manifest has a low cost, so a hard-fail check there is friction without much payoff. The first one, the total-bytes ceiling, is worth doing if the bundle trend keeps climbing; right now the per-chunk budgets are holding and the login surface is unchanged at about a hundred ten kilobytes gzipped, so it is not urgent.

The other thing worth flagging, again, is the operator-side verification debt. Five mechanism conversions and a full punch list have shipped this session-week, all with gate-level confidence, and the live browser verification against the real Netlify and Supabase deploy is still pending on your side. The guardrails make the repository harder to break; they do not substitute for walking the actual flows on a real phone. When you have time, the verify checklist in `PLAN.md` plus the cut-specific walks in the recent comms are the sequence.

## The bigger picture

What this session completes is a quiet but real milestone: the wallet's doctrine is now legible in its test results. Before this session-week, `CLAUDE_ROOT.md` was a document a Carpenter had to read, internalize, and remember to comply with. After five mechanism-over-prose conversions — manifest coverage, `tapit-attest` integrity, bundle budgets, file size, and keys-never-leave — the rules that matter are checks that fail. A Carpenter who never reads the doctrine, or reads it and forgets it, or is a different model entirely six months from now, still cannot merge a build that logs a passphrase, re-implements an `envelope` primitive, bloats a chunk past budget, lets a file grow past eight hundred lines, or ships a feature folder without a registered manifest. The doctrine stopped being something you have to hold in your head and became something the repository holds for you. That is exactly what non-negotiable five — "mechanism over prose, the fix is a check that fails, not another paragraph" — was asking for, and the gate fence section's instruction "when a rule matters enough to enforce, add a check, do not add prose here" is now satisfied for every rule it names.

The deeper point is about where attention goes. Every mechanical check is a withdrawal from the Carpenter's attention budget that never has to be repaid. The keys-never-leave audit used to cost a deliberate review pass on every commit that touched the wallet object or the passphrase; now it costs nothing, it just runs. That reclaimed attention is the actual product of this session — not the two test files, but the freeing-up of the scarce thing. The next time you point the Carpenter at a feature, more of the session can go to the feature and less to remembering the rules, because the rules enforce themselves. A wallet that protects a person's sovereign identity for decades needs exactly that property: the safety does not depend on whoever is currently holding the chisel remembering to be careful. It depends on the checks.

The wallet's feature surface is unchanged this session. What changed is that the most important promise the wallet makes — your keys never leave unencrypted — is now something a test enforces on every run, not something a person has to vouch for. That is the right note to pause on. When you come back, it is either browser-verify findings against the live deploy, or a new direction; the gate fence itself is complete.
