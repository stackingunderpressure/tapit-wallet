## What tapit-wallet is

A person's sovereign identity wallet. It generates and holds the
user's keypair, coordinates key rotation through a succession
chain, and is the Merkle holder of the signed attestations that
make up their verifiable life. It is the only place a user's
private keys live. Other apps do not hold keys — they connect to
this wallet over the Layer 2 signing pathway. Other wallets
connect peer-to-peer over the Layer 3 network.

It is the MetaMask model done for attestations instead of
transactions: one identity per person, every app routes through
it, every wallet reachable by every other.

## The four layers

- **Layer 1 — the Wallet core object.** ALREADY BUILT. It lives
  in the `tapit-attest` library (`tapit-attest/src/core/
  wallet.ts`), inherited from the chassis. Keypair, succession,
  the attestation holder, sign-both-ways, encrypted backup, sync,
  peer recovery. This app is built *around* that object.
- **Layer 2 — the inter-app connection pathway.** Apps send the
  wallet a `SignRequest`; the user approves; the wallet returns a
  signature. Cross-process.
- **Layer 3 — the Mycelium peer network.** Wallet-to-wallet.
  NOT built until it has its own `MYCELIUM_NETWORK_SPEC.md`.
- **Layer 4 — the frictionless surface + the wallet bot.** The
  app UI and a conversational guide for non-technical users.

Build bottom-up. See `PLAN.md`.

## tapit-attest is inherited — never re-implement it

The chassis copies the whole `tapit-attest` package into this
repo's root as `tapit-attest/`. It carries the signed-attestation
primitive and the `Wallet` class. This app consumes it as a
`file:` dependency (`"tapit-attest": "file:./tapit-attest"` in
`package.json`, added when the app shell is scaffolded in
job-001). Do NOT rewrite the envelope, the signing, the field
tree, or the `Wallet` object. One library across the whole fleet
is the compatibility guarantee — re-implementation is the
thousand-incompatible-islands failure mode.

## Feature folder count

Per the staged feature stubs in `appcommander/manifests/`:
- `auth` — login, session, the user's account
- `wallet-core` — keypair + identity + succession + the
  attestation holdings view; the heart of the app
- `app-connections` — Layer 2: apps requesting signatures, the
  approval surface
- `backup-recovery` — encrypted backup + peer-rebuild recovery
- `wallet-bot` — Layer 4: the conversational guide

That's **5 features** — not 32, not "all of AppCommander's
features." If the inventory you walk pulls in more, you're seeing
AppCommander's registry leaking in. Look only at what's in this
repo's `src/features/` folder and `appcommander/manifests/`.

## Path conventions

The cockpit-style metadata folder is `appcommander/` (no leading

## Manifests are .ts files, not a single manifest.json

Each feature folder gets its own `manifest.ts`. There is no
`manifest.json`, no combined manifest at the repo root. The
shared type lives at `appcommander/manifests/_shared.ts` for the
staged stubs; those move into `src/features/<slug>/manifest.ts`
once each feature has real code.

## Operator vs user

"user" = the person who installs and owns a Tapit Wallet.
"operator" = Thomas, the builder/deployer of the wallet app
itself. When the Foreman says "what the user wants," they mean
the wallet's owner. "What the operator decided" means Thomas.

## Monetization flag — every feature gets one

tapit-wallet ships with a feature-flag util at
`src/shared/lib/featureFlag.ts` (Frank-scaffolded). Every new
feature has an entry with a default: `'on'` (free for everyone),
`'off'` (disabled / paused), or `'paid'` (gated behind a paid
tier). When you build a feature flagged `monetizable: true` in
the manifest, wrap its entry points in `featureFlag.check(slug)`
from day one.
